**문장을 바꾸면 조용히 깨지는 곳 둘.** 영어는 한국어 문장을 정규식으로 번역한다 — 서버 `stage5._review_evidence_en`,

문장을 바꾸는 작업은 이 둘을 같이 걷어내야 한다(아래 "어디서 만드는가").

옛 문장이 어려운 이유는 여섯 가지로 갈린다. 문장 하나만 고쳐서는 안 풀린다.

| 원인 | 예 |
|---|---|
| 왜 보는지가 없다 | "7일 안에 몰림"이 왜 중요한지, 5.5%와 13.5% 차이가 큰 건지 판단 근거가 없다 |
| 통계 용어 | 중앙값 · 95% 신뢰구간 · 기준선 · 대조군 · 부류 |
| 내부 용어 누출 | "관계·행동 축 관측 (리뷰 본문 아님)", "규칙 기반 집계", "산출물 미탑재 — pcparts_product_risk.json" |
| 행동 지시가 없다 | 읽고 나서 그냥 사면 되는지, 리뷰를 직접 봐야 하는지 모른다 |
| 다 보여준다 | 중앙값과 같은 값(몰림 5.6% vs 5.5%)까지 전부 나열해 신호가 묻힌다 |
| 모순 | Ryzen 5 5600은 헤드라인 "특이 없음"인데 바로 뒤 규칙 집계는 "기준선 초과" |

`signals` 로 숫자만 넘기면 첫 두 줄(왜 보는지 · 통계 용어)이 프론트 몫으로 옮겨갈 뿐 없어지지 않는다 — 막대그래프에
"중앙값" 선을 그으면 같은 문제다. 그래서 문장은 서버가 만든다.

## 원칙 (docs/decisions/0001 과 충돌하지 않게)

1. **숫자는 코드가, 말은 템플릿이.** 값·중앙값·건수는 지금 그대로 두고 문장 껍데기만 바꾼다. 원문 문장은
   `GET /reviews/summary` 의 `summaries` 에 그대로 남기고, 유저용 문장은 `ReviewBriefOut` 에 **별도 필드**로
   낸다 — 심사·검토용 원문과 유저용 문장을 분리.
2. **판정어를 쓰지 않는다.** 조작·가짜·의심스럽다 대신 "살펴볼 점". `_BANNED_IN_DRAFT` 에 `조작`·`가짜` 를 추가해
   코드로 막는다.
3. **중앙값을 넘은 것만 문장으로, 나머지는 접는다.** `[3-B]` 가 `REVIEW_AXIS_EXCESS`(2배)로 고른 지표를 그대로 쓴다.
4. **면책 문장은 한 번만, 쉬운 말로.** 지표마다 붙는 "상품 단위 신호이며…" 를 카드 하단 한 줄로 모은다.

## 3층 구조

```
[1층 헤드라인]  리뷰 37건 · 사기 전에 살펴볼 점 2가지
[2층 살펴볼 점] · 리뷰 5건(약 14%)이 같은 일주일에 몰려 올라왔어요.
                  비슷한 부품은 보통 리뷰의 5% 정도만 같은 일주일에 몰려요.
                · 리뷰 37건 중 8건(약 22%)은 '이 리뷰 하나만 남긴 계정 · 계정 활동이 짧음'
                  같은 특징이 둘 이상 겹쳐요. 리뷰가 37건뿐이라 이 숫자는 참고만 하세요.
[3층 자세히 ▾]  전체 지표 표(값 · 비슷한 부품 보통값) + 아마존에서 직접 보기 ↗ + 원문 문장
──
리뷰가 올라온 '모양'만 본 결과예요. 어떤 리뷰가 진짜인지는 판단하지 않아요.
```

특이 없는 경우(Noctua NH-D15, 748건)는 1층 한 줄로 끝 — **"리뷰 748건 · 비슷한 부품들과 다른 점 없음"**. 2층 생략.
(Ryzen 5 5600 은 규칙 집계 6.1% 의 CI 하한 3.2 가 기준선 3.1 을 넘어 "살펴볼 점 1가지" 가 된다 — "먼저 결정할 것" 2.)

### 영어 (`lang="en"`)

데모는 영어로 진행한다(`src/engine/lang.py`, 2026-09-14). 영어 경로는 이미 코드에 있다 — `observations(lang="en")` 은
카드 문장을 건너뛰고 수치에서 다시 렌더하고, `SuspectCountFile.sentence` · `_review_line` 은
`L(lang, ko, en)` 으로 갈린다. 지금 영어 출력:

> 5 of 37 reviews (13.5%) arrived within a 7-day window — median across products 5.5% / 26 reviewers also appear on
> other products (285 connected products) — median 60 / 903 / 5-star share 49% — median 67% / 8 of 37 reviews (21.6%)
> trip 2+ suspicion indicators (all demo products 3.1%) — 95% CI [9.8, 38.2] · above the baseline

한국어와 같은 규칙(%로 통일 · 독립문 · "only" 는 초과 지표에만 · 판정어 금지 · 느낌표 금지)으로 같은 자리에 쓴다.

| 지표 | 층 | 제안 (en) |
|---|---|---|
| burst7 | 2 | {count} reviews (about {%}%) were posted within the same week. For similar parts, usually only about {median}% of reviews land in the same week. |
| burst7 출시 첫 주 | 3 | That week was right after launch, so the bunching looks natural. |
| prolific_rate | 2 | {%}% of the reviewers are accounts with more than 30 reviews. For similar parts, usually only {median}% of reviewers have written that many. |
| one_off_rate | 3 | {%}% of the reviewers are accounts with this one review only. For similar parts it is usually {median}%. |
| short_span_rate | 3 | {%}% of the reviewers are accounts active for 30 days or less. For similar parts it is usually {median}%. |
| verified_rate | 3 | {%}% of the reviews carry a verified-purchase mark. For similar parts, usually {median}% of reviews carry it. (Reviews from free-sample or gift programs may not carry the mark.) |
| p5 | 3 | {%}% of the reviews are 5-star. For similar parts, usually {median}% are 5-star. |
| shared_reviewers / deg | 3 | 보류 — 한국어와 같이 "먼저 결정할 것" 1 |
| 규칙 집계 | 2 | {k} of {n} reviews (about {%}%) share two or more traits such as '{two indicator names}'. [n<100 이면] With only {n} reviews, treat this number as a rough guide. |

지표 이름(en): burst → posted within the same week · prolific → account with 30+ reviews · one_off → account with this one
review only · short_span → short-lived account · unverified → no verified-purchase mark.

- `src/engine/lang.py` 독스트링 "리뷰 관측 문장은 데이터라 한국어 그대로" 는 낡았다 — `observations(lang="en")` 은
  이미 수치에서 다시 렌더한다. 유저용 템플릿이 들어가면 두 언어 다 수치에서 렌더하고, 배치가 한국어로 적어 둔 카드
  문장은 3층 "원문" 에만 남는다. 독스트링을 그에 맞춘다.

## 템플릿 규칙 (위 표에서 뽑은 것 — 새 지표를 추가할 때도 지킨다)

1. 값은 **%로 통일**, 건수는 괄호로 같이 — "리뷰 5건(약 14%)". "절반·거의 다·넷 중 하나" 같은 어림 표현을 쓰지 않는다.
2. 비교문은 **독립문** — 주어·서술어를 다시 쓴다. "보통은 거의 다 있어요" ✗ → "보통은 구매 확인 표시가 거의 다 있어요" ✓
3. "**만**"은 중앙값을 넘어서 뽑힌 지표(몰림·다작)에만 쓴다. 양방향 지표(5점 비율·1건 계정)에는 쓰지 않는다 —
   "67%만" 은 "이 부품은 많다" 는 방향을 은근히 준다.
4. 짧게 줄이되 **"왜"는 지우지 않는다.** 괄호 한 절이면 된다 — 구매 확인의 "(체험단·증정…)", 기간 밖의 "(2023년 9월 이후 출시)".
5. 느낌표·"주의" 같은 경고 표지를 쓰지 않는다. 소표본 문장은 앞 문장을 **약하게** 하려고 붙이는 것인데 "주의!" 가
   부품 옆에 있으면 부품이 위험하다는 경고로 읽힌다.

## 템플릿에 생기는 분기

- **규칙 집계 소표본 문장**: 이미 있는 이항 95% CI 를 쓴다. CI 하한이 기준선 이하면 "살펴볼 점" 에 올리지 않고
  (코드가 이미 "구별되지 않음" 으로 판정) 3층에만 둔다. 올릴 때 n<100 이면 소표본 문장을 붙인다.
- **관측 없음 사유 3종**: 지금 `risk_store_note()` 는 "문턱 미만이거나 기간 밖" 을 한 문자열로 낸다 — 산출물에
  없다는 것만 안다. "30건보다 적어요" 를 사실대로 내려면 `data/parts_asin_map.csv` 로 갈라야 한다:
  `asin` 없음 + `note` → 기간 밖, `asin` 있는데 산출물에 없음 → 문턱 미만, 산출물 자체를 못 읽음 → 불러오지 못함.

## 어디서 만드는가

| 방식 | 판단 |
|---|---|
| **서버 코드 템플릿** — `review_repo` 또는 `review_service` 에 렌더러, 두 언어 다 **수치에서** 렌더 | **채택.** 지표가 8종뿐이라 분기를 다 쓸 수 있고, 테스트로 고정되며, 판정어가 새지 않는다. 정규식 번역(`_review_evidence_en` · `logs.js`)을 걷어낼 수 있다 |
| LLM 재서술 (stage5 패턴: structured output + 금지어 + 템플릿 fallback) | 카드에는 쓰지 않는다. 실호출에서 "강력한 성능" 같은 평가어가 샌 전례가 있고 숫자 보존 검사를 더 얹어야 한다. 회의의 "3~4줄 요약" 에서 리뷰 한 줄을 언급할 때만 — 입력은 위 템플릿 문장, 출력 검사는 기존 `_BANNED_IN_DRAFT` |
| 프론트에서 변환 (`signals` 숫자 → 문장) | 기각. 중앙값이 `signals` 에 없고, 영어 분기·결과 에이전트 `explain` · 로그와 갈라진다. 지금 `logs.js` 가 정규식으로 하는 일이 그 예다 |

### `ReviewBriefOut` 에 얹을 것 (develop `36943c0` 의 자리 위에)

```
review.cleansing_summary   ← 면책 한 줄. 지금 비어 있는 _CLEANSING_SUMMARY_TEXT 를 위 "면책" 문장(ko·en)으로
                              바로 채운다 — "담당자가 정해줄 고정 해석 안내문" 이 이것이다
review.signals.<지표>.median ← 대조군 중앙값(ProductRiskStore.controls). 막대그래프의 기준선용. 지금 없다
review.plain               ← 새 필드 {headline, points[], details[], sources[], verify_url, reason}
    headline : 1층 한 줄. 관측이 없으면 사유 문장이 여기 온다
    points   : 2층 — 중앙값을 넘어 뽑힌 지표 + (CI 하한이 기준선을 넘을 때) 규칙 집계, 각각 템플릿 문장 하나
    details  : 3층 — 나머지 지표 문장 (양방향 지표는 항상 여기)
    sources  : 3층 — 산출물 원문 (GET /reviews/summary 의 summaries 와 같은 문장, 검토자용)
    verify_url : 아마존 상품 페이지
    reason   : 관측이 없을 때 사유 코드 — below_threshold | out_of_period | no_match | unmapped | unavailable.
               프론트가 이걸로 분기한다(건수 타일 숨김 등). 관측이 있으면 null
```

`plain` 은 `lang` 을 따른다(`review_brief(product_key, lang)`). `signals` 는 그대로 두고 `median`·`baseline` 만 더했다 —
숫자는 그래프용, `plain` 은 읽기용. 유저용 문장에 판정어·통계 용어가 없는 것은 `tests/test_review_plain.py` 가 막는다
(stage5 LLM 초안의 `_BANNED_IN_DRAFT` 에 판정어를 더하는 것은 별도 — 데모 직전이라 LLM 경로는 손대지 않았다).

프론트(03 리뷰 슬라이드, `results.js tfReviewPlainHtml`): 리뷰 수 타일 아래에 `plain.headline` → `plain.points` →
"자세히 ▾" 에 `plain.details` · 원문(`sources`) · 아마존 링크 → `cleansing_summary` 하단. `plain.reason` 이 있으면
사유 한 줄만 그리고 **리뷰 수 타일과 면책을 숨긴다**(표시용 건수 7~13 이 "데이터 없어요" 옆에 서면 모순 — "먼저 결정할
것" 3 을 프론트 쪽에서 이렇게 가정). `signals` 막대그래프는 아직이다. `checks` 는 손대지 않는다.

정규식 번역 제거: 서버가 두 언어를 수치에서 렌더하면 `stage5._review_evidence_en` · `_risk_store_note_en` 과
`logs.js tfLegacyLogText` 의 리뷰 문장 규칙이 필요 없다. 남겨 두면 옛 문장에만 맞는 죽은 규칙이 된다.

## 먼저 결정할 것 (문장을 고치기 전에 데이터가 걸린다)

1. **`shared_reviewers` 절대수 비교.** 리뷰 4,189건 상품은 공유 리뷰어 3,073명 vs 중앙값 60명 — 리뷰가 많으면
   무조건 "초과" 로 읽힌다. 쉬운 말로 옮기면 오해가 더 커진다. `shared/n` 비율(Ryzen 94%)이나 `neighbor_density` 로
   바꾸든지, 3층 표에만 숫자로 두든지.
2. **헤드라인과 규칙 집계의 기준 불일치.** 헤드라인은 `EXCESS_KEYS`(burst7·prolific) 2배 기준, 규칙 집계는
   5지표 조합 + CI 하한 기준이라 "다른 점 없음 + 규칙 집계 초과" 가 같이 나온다. 1층 "살펴볼 점 {k}가지" 의 k 를
   한 기준으로 세든지(2층에 올라가는 문장 수 = k), 규칙 집계를 3층으로 내리든지. **구현은 전자로 가정했다** —
   k = 2층 문장 수, 규칙 집계는 CI 하한이 기준선을 넘을 때만 2층. 후자로 정하면 `review_plain.render` 한 줄이다.
3. ~~표시용 리뷰 건수와 "리뷰 데이터가 없어요" 의 충돌.~~ **해소** — `docs/decisions/0003`: 모르는 리뷰 수는
   `total_count: null` 로 내고 표시용 7~13 은 없앴다.
