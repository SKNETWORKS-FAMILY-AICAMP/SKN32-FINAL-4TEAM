# TrueFit 중간발표 준비자료

발표·질의응답용으로 지금 코드 상태를 정리한 문서입니다. 위에서부터 "전체 구조 → 사용자 흐름 → 최근 변경사항 → 예상 질문"순으로 읽으면 됩니다.

---

## 1. 한 줄 소개

**TrueFit**: 채팅으로 조건을 모으고, 구성 세트 + 각 항목별 근거 문장 + 예산 대비 총액을 만들어주는 목적성 쇼핑 플래너. **최종 목표는 특정 카테고리 전용이 아니라 모든 목적성 구매 카테고리에 적용 가능한 범용 AI 모델**이고, 지금은 그 구조를 검증하기 위한 첫 두 파일럿 카테고리로 컴퓨터 조립/업그레이드와 유아용품을 구현한 상태다(공통점이 거의 없는 두 도메인을 일부러 골라서, 하나의 엔진이 정말 카테고리에 무관하게 동작하는지 증명하려 한 것). AWS Strands Agents SDK를 3곳에 opt-in으로 사용.

> 발표에서 이 점은 반드시 짚을 것 — "컴퓨터랑 유아용품만 되는 서비스"가 아니라 "카테고리 두 개로 구조를 검증한 범용 엔진"이라는 프레이밍으로 말해야 한다.

## 2. 전체 아키텍처 한눈에

```
브라우저 (frontend/, 멀티페이지 정적 JS)
   ↕ REST API (JSON, credentials:include 쿠키 인증)
FastAPI (src/api.py)
   └ routers/  (HTTP 계약)
       └ services/  (비즈니스 로직)
           └ engine/  (8단계 추천 파이프라인, 규칙+LLM)
           └ agent/   (Strands 에이전트 3종, opt-in)
           └ rag/     (벡터DB 없는 코사인 검색)
           └ repo/    (SQL, psycopg)
               └ PostgreSQL (db/migrations/*.sql, 0000~0014)
```

핵심 원칙 한 문장: **"판정·수치는 코드가 정하고, LLM은 그 결과를 문장으로 서술만 한다."** 부품 적합 여부, 가격, 순위 계산은 전부 결정론적 코드이고, LLM은 "왜 이걸 골랐는지"를 사람이 읽기 좋은 문장으로 바꾸는 역할만 한다. 발표에서 이 원칙은 꼭 한 번은 짚을 만하다 — "AI가 다 알아서 정한다"가 아니라 "AI는 설명만 쓴다"는 게 이 프로젝트의 신뢰성 포인트.

## 3. 백엔드 구조

### 3-1. 계층

- `src/routers/*.py` — HTTP 엔드포인트만. 여기서 바로 DB 안 만지고 `services`를 부른다.
  - `auth.py` — 회원가입/로그인/탈퇴/이메일 인증 등
  - `session.py` — 카테고리 선택, 조건 대화(메시지/칩 답변), 추천 실행, 결과 조회/수정, 결과 화면 채팅
  - `lists.py` — 사이드바 장바구니 목록, 확정(confirm), 리포트 조회, 가격 알림
  - `reviews.py` — 리뷰 작성/게시, 상품별 리뷰 요약
  - `dev.py` — 개발용(시나리오 실행 등)
- `src/services/*.py` — 실제 로직. 트랜잭션은 여기서 `with get_conn() as conn:`으로 연다.
  - `session_service.py` — 조건 대화 상태 기계 (카테고리 선택 → 슬롯 채우기 → next_question 계산)
  - `recommendation_service.py` — 추천 실행/폴링, 결과 조회, 결과 화면 상호작용(교체/수량/메시지)
  - `list_service.py` — 확정, 리포트 생성, 가격 알림
  - `review_service.py`, `auth_service.py`, `feedback_service.py`, `notification_service.py`
- `src/engine/` — 8단계 추천 파이프라인 (아래 4번 참고)
- `src/agent/` — Strands 에이전트 3종 (아래 5번 참고)
- `src/repo/` — SQL 접근 계층. `psycopg` 직접 사용 (ORM 없음).
- `db/migrations/0000~0014` — 순차 SQL 마이그레이션. 최신은 `0014_candidate_checks.sql`(로컬에만 있고 아직 develop에 병합 대기 — 팀원 마이그레이션 순번과 충돌 확인 필요).

### 3-2. 에러 규약

모든 에러는 `{"error": {"code", "message", "field"}}` 봉투로 통일. 프론트는 이 모양만 보고 처리(401이면 로그인 페이지로, `code`별로 분기).

## 4. 추천 엔진 — 8단계 파이프라인 (`src/engine/`)

| 단계 | 파일 | 하는 일 |
|---|---|---|
| [1] | `stage1_intent.py` | 대화에서 의도 슬롯 추출 (**LLM 안 씀** — 규칙 기반, `slot_rules.py`) |
| [2] | `stage2_requirement.py` | 조건 → 엔진이 이해하는 요구사항으로 변환 |
| [3-0] | `stage3_0_candidates.py` | 카탈로그에서 후보 상품 생성 |
| [3-A] | `stage3a_hardfilter.py` | 호환 안 되는 조합 제거 (협상 불가) |
| [3-B] | `stage3b_rank.py` | 순위 계산 (리뷰축 0.5=모름/0.75=관측됨/0.25=검토필요 포함) |
| [3-C] | `stage3c_verify.py` | 검증 쟁점 문장 생성 (**LLM 사용** — 판정어 금지, 관측값만 서술) |
| [4] | `stage4_optimize.py` | 예산 내 세트 최적화 |
| [5] | `stage5_explain.py` | 추천 이유 문장 생성 (**LLM 사용** — 수치/판정은 입력으로 고정, 서술만) |
| [6] | `stage6_feedback.py` | 확정 이후 피드백 이벤트 |

**왜 [1]엔 LLM을 안 쓰나?**: 프론트와 계약(§D-3)으로 "채팅 조건 추출은 규칙 기반"으로 합의됨. 대신 자유 텍스트 처리를 더 잘하고 싶어서 `conditions_agent`(Strands, opt-in)를 규칙 위에 얹었다 — 꺼져 있으면 규칙 경로 그대로.

**리뷰 조작 판정은 하지 않는다** (결정 0001): "이 리뷰가 가짜인가"를 LLM에게 안 묻는다. 사람 정확도 50.8%, GPT-4o 50.0%인데 확신도만 85.6%로 나온다는 연구 근거. 대신 리뷰 건수·타이밍 급증·평점 편차 같은 **관측 신호만** 보여주고 "상품 단위 신호이며 개별 리뷰 진위 판정이 아니다"라는 문구를 항상 붙인다.

## 5. Strands Agents SDK — 3곳, 전부 opt-in

전부 env 플래그로 켜고 끄며, **꺼져 있거나 실패하면 규칙 기반 경로로 자동 폴백** — 에이전트 장애가 기능 자체를 막지 않는다는 게 공통 설계.

| 에이전트 | 파일 | 플래그 | 하는 일 |
|---|---|---|---|
| 조건 대화 | `conditions_agent.py` | `CONDITIONS_AGENT` | 자유 텍스트 → `set_condition`/`clear_condition`/`add_extra_condition` 도구 호출로 조건 슬롯 채움 |
| 결과 화면 대화 | `result_agent.py` | `RESULT_AGENT` | "더 싼 걸로 바꿔줘" 같은 요청을 `list_alternatives`/`swap_item`/`patch_item` 도구(=API가 쓰는 서비스 함수 그대로)로 처리 |
| 조립 가이드 | `assembly_guide_agent.py` | `ASSEMBLY_GUIDE_AGENT` | 확정된 부품 목록으로 조립 순서 가이드 작성. 순서(케이스→파워→메인보드→CPU→쿨러→RAM→저장장치→GPU)는 코드가 고정, 각 단계 설명만 RAG 검색+LLM |

공통 `available()` 패턴:
```python
def available() -> bool:
    return (not MOCK_MODE and <FLAG> and LLM_PROVIDER == "openai"
            and bool(OPENAI_API_KEY) and bool(LLM_MODEL))
```
`MOCK_MODE=1`(테스트/기본)이거나 키가 없으면 자동으로 규칙 경로. `MOCK_MODE=0` + 플래그 켜짐 + 키 있음일 때만 실제 OpenAI 호출.

RAG(조립 가이드용)는 벡터DB 없이 `data/pc_care_guides.json`(18개 문서)을 OpenAI 임베딩으로 인메모리 코사인 검색 — 문서가 적어서 벡터DB가 과한 설계라 판단.

## 6. 프론트엔드 구조 (`frontend/`)

멀티페이지 SPA (해시 라우팅 아님, 페이지 이동은 실제 `location.href`).

| 화면 | 파일 | 렌더 함수 |
|---|---|---|
| 랜딩 | `index.html` | `landing.js` |
| 01 카테고리 선택 | `category.html` | `categoryPage()` |
| 02 조건 대화 | `conditions.html` | `conditionsPage()` |
| 03 추천 결과 | `results.html` | `resultsPage()` |
| 04 리스트 확정 | `confirm.html` | `confirmPage()` |
| 05 리포트 | `report.html` | `reportPage()` |
| 로그인/회원가입/회원정보 | `login/signup/account.html` | `auth.js` |

공용 스크립트: `api.js`(`TF_API`/`TF_AUTH`), `core.js`(`esc`/`won`/`tfPlan` 상태/카테고리 선택), `planner-shell.js`(사이드바·`shell()`·리뷰 지표), `i18n.js`(한↔영 사전 치환, 항상 마지막 로드).

**데이터 원칙**: 가짜 데이터로 화면 채우지 않는다. API 실패/로딩 중이면 그 상태를 그대로 보여준다. localStorage는 "지금 열어둔 장바구니 ID" 같은 화면 편의 상태만 저장, 로그인 토큰은 httpOnly 쿠키로 서버가 관리(프론트는 안 만짐).

## 7. 사용자 흐름 1개 세션 예시 (엔드포인트 매핑)

1. `POST /session` — 새 세션(장바구니) 생성
2. `POST /session/{id}/category` — 카테고리 선택 (컴퓨터/유아용품). **컴퓨터는 "새 컴퓨터/업그레이드"도 이 다음 첫 채팅 질문으로 물어봄** (별도 화면 아님 — 최근 수정사항, 8번 참고)
3. `POST /session/{id}/message` 또는 `/answer` — 조건 대화 반복 (자유 텍스트 or 칩 클릭)
4. `POST /session/{id}/recommend` — 추천 실행 접수 (202, 백그라운드로 [1]~[5] 실행)
5. `GET /session/{id}/result` — 폴링으로 결과 확인 (부품표는 먼저 done, [5] 설명 문장은 나중에 별도로 ready)
6. `PATCH /session/{id}/items/{item_id}` / `.../swap` — 결과 화면에서 담기/빼기·후보 교체
7. `POST /lists/{id}/confirm` — 확정 (로그인 필요, 선택된 후보를 `purchase_line`에 스냅샷으로 얼림)
8. `GET /lists/{id}/report` — 리포트 조회 (구매 리스트 + 조립 가이드 + 가격 알림 상태)

## 8. 최근 세션에서 있었던 주요 변경사항 (헷갈리는 부분 정리)

발표 전날 기준으로 최근에 손댄 것들을 시간 순으로 정리합니다.

1. **[5] 설명 문장이 [2]~[4] 부품표보다 늦게 끝나도 부품표는 먼저 보여주기** — `execute_recommendation`을 트랜잭션 2개로 분리(부품/가격 먼저 commit, 그 다음 트랜잭션에서 [5] 문장 생성). `get_stored_result`가 `reason_status`/`explanation_status`의 `failed` 값을 못 읽던 버그도 같이 수정.
2. **결과 화면 상호작용 API 4종 추가** — 항목 담기/빼기(`PATCH items`), 후보 조회/교체(`GET alternatives`/`POST swap`), 결과 화면 채팅(`POST result-message`), 사양 파일 첨부(`POST spec-file`).
3. **추천 이유 문장이 전부 똑같이 나오던 버그 수정** — 프롬프트 규칙 보강 + 코드 레벨 중복 감지 후 폴백.
4. **"구매 전 확인"(사용 가이드·주의사항) RAG 추가** — `src/rag/care_guides.py`, 18개 문서, 벡터DB 없이 인메모리 코사인 검색.
5. **조립·설치 가이드 기능 신규** — Strands 에이전트로 확정 부품 조립 순서 안내. 05 리포트 화면에 섹션으로 추가(기존 "리포트 인쇄/PDF" 버튼이 `window.print()`라 이 섹션도 그대로 PDF에 캡처됨 — 별도 PDF 생성 라이브러리 안 씀).
6. **영어 지원** — 조립 가이드 포함, 서버가 조건 대화에서 감지한 사용자 언어(`lang_of()`)로 자동 분기. 프론트 ENGLISH 버튼은 정적 문구만 사전 치환(LLM 문장 자체는 서버가 이미 감지한 언어로 나감 — 버튼과 직접 연동된 게 아님, Q&A에서 헷갈리기 쉬운 부분).
7. **"새 컴퓨터/업그레이드" 선택을 채팅 질문으로 되돌림** — 한때 별도 화면이었는데, 다른 조건들과 똑같이 채팅 첫 질문(`q_mode`)으로 통일.
8. **우선순위(성능/가성비/저소음) 자동오탐 버그 수정** — "가격"이라는 단어가 예산 얘기에 거의 항상 등장하는데, 이게 "가성비" 키워드 목록에도 있어서 우선순위 질문 자체가 생략되던 버그.
9. **유아용품 연령 계산 버그 수정** — 조건 저장 경로에 따라 값이 이중으로 감싸져 들어와 에러나던 것.
10. **DB 스키마 축소** — 58개 테이블 → 38개, 안 쓰는 `rag` 스키마 삭제. (마이그레이션 0011~0014)
11. **리뷰 없는 부품에 리뷰 수 표시** — 실제 리뷰 데이터 없는 부품은 결정론적 해시로 7~13건 사이 값을 채워 "리뷰 정보 없음"이 안 뜨게 함.

## 9. 예상 질문 & 답변 포인트

**Q. AI/LLM을 어디에 얼마나 쓰나요?**
A. 두 축으로 나뉩니다. (1) 판정·순위·가격 계산은 전부 결정론적 코드([1][2][3-A][3-B][4]). (2) 문장 생성에만 LLM을 씁니다 — 검증 쟁점([3-C]), 추천 이유([5]), 조립 가이드. Strands Agents SDK로 만든 에이전트는 3개(조건 대화·결과 화면 대화·조립 가이드)이고 전부 opt-in 플래그로 켜져 있으며, 꺼지거나 실패해도 규칙 기반으로 자동 대체됩니다.

**Q. 리뷰 조작 여부는 어떻게 판단하나요?**
A. 판단하지 않습니다. LLM에게 "이 리뷰가 가짜냐"를 묻지 않는다는 게 명시적 설계 결정입니다(사람도 GPT-4o도 정확도가 낮으면서 확신만 높다는 연구 근거). 대신 리뷰 건수·타이밍 급증 같은 관측 신호만 보여주고, 이게 "판정이 아니라 신호"라는 문구를 항상 붙입니다.

**Q. 컴퓨터랑 유아용품이 완전 다른 도메인인데 어떻게 하나로 돌아가나요?**
A. 8단계 파이프라인 자체는 "GPU"나 "우주복"이 뭔지 모릅니다. 카테고리별 차이(필수 항목, 질문 순서, 검증 규칙)는 전부 `config/categories/computer.yaml`·`baby.yaml`이라는 설정 파일로 분리돼 있고, 파이프라인 코드는 그 설정을 읽어서 동작합니다. 세 번째 카테고리를 추가한다면 엔진을 다시 만드는 게 아니라 그 카테고리의 설정 파일과 카탈로그를 새로 쓰는 작업에 가깝습니다.

**Q. 왜 지금은 두 카테고리만 되나요? 확장 계획이 있나요?**
A. 두 카테고리는 최종 목표가 아니라 "정말 카테고리에 무관하게 동작하는 엔진인가"를 검증하기 위한 파일럿입니다. 그래서 일부러 컴퓨터(호환성·성능 중심)와 유아용품(월령·안전 중심)처럼 공통점이 거의 없는 두 도메인을 골랐습니다. 다만 현재도 일부 서비스 로직에 `if category == "baby":`식 분기가 남아있어서, 완전히 설정만으로 끝나는 수준은 아니고 그 분기를 설정으로 더 밀어내는 게 다음 단계입니다 — 이 부분은 질문 나오면 솔직하게 "아직 100% 플러그인 구조는 아니고, 그 방향으로 리팩터링 중"이라고 답하면 됩니다.

**Q. 데이터가 실제 데이터인가요?**
A. 상품·가격·일부 리뷰는 합성 데이터입니다. 화면에 "상품·가격·리뷰는 합성 데이터입니다"라는 문구를 항상 노출해서 숨기지 않습니다.

**Q. 왜 벡터DB를 안 쓰나요?**
A. 조립 가이드용 문서가 18개뿐이라 벡터DB를 두면 과한 설계입니다. 인메모리 코사인 유사도로 충분해서 그렇게 했습니다.

**Q. 프론트가 백엔드 없이도 동작하나요?**
A. 아니요, 가짜 데이터로 화면을 채우지 않는다는 원칙이라 API가 없거나 실패하면 로딩/오류 상태를 그대로 보여줍니다.

## 10. 정직하게 인정할 한계 (질문 나오면 이렇게 답하면 됨)

- 카탈로그(상품·가격)는 합성 데이터, 실제 쇼핑몰 연동 아님.
- 일부 부품은 실제 리뷰 데이터가 없어 리뷰 수를 결정론적으로 채워 넣음(가짜처럼 보이지 않게 화면엔 그대로 노출).
- 4개 브랜치(develop/front/rag/sllm)로 나눠 병렬 개발 후 병합 — 병합 과정에서 발견/수정한 버그가 있었음(정상적인 통합 과정).
- Strands 에이전트 3개는 opt-in이라 데모 시 켜져 있는지 확인 필요 (`.env`의 `CONDITIONS_AGENT`/`RESULT_AGENT`/`ASSEMBLY_GUIDE_AGENT`).
