# P5 실행 보고 — 추천 실행·저장·결과·후보 편집 API

## 실제로 구현한 것

CONTRACTS.md와 `reports/sync-2026-09-13.md`의 델타 지시대로, P1(`normalize_baby_conditions`/
`load_owned_draft`)·P2(`build_baby_requirements`/`persist_baby_requirements`/
`get_baby_candidates`)·P3(`verify_and_persist_baby_candidate`)·P4(`run_baby_optimizer`)를
**코드 변경 없이 그대로 재사용**해, `start_recommendation`/`execute_recommendation`/
`get_stored_result`의 baby 분기와 `PATCH 항목`/`GET 대안`/`POST 교체`/`POST 결과-메시지`
HTTP 엔드포인트를 실제로 배선했다. `docs/agent-tasks/baby/reports/artifacts/p4-integration-probe.py`가
보여준 실제 호출 순서(P1→P2→P3→P4)를 독립 스크립트가 아니라 `src/services/recommendation_service.py`
안의 실제 HTTP 실행 경로로 옮겼다.

### 1. `start_recommendation` (요청 트랜잭션 안, `src/services/recommendation_service.py`)

- baby 분기 추가: `compute_missing`(기존 함수, computer/baby 공용)으로 422 조건 미충족을
  run 생성 전에 막고, `has_running_run`으로 409 `run_in_progress`를 막은 뒤에만
  `build_baby_requirements`+`persist_baby_requirements`를 **같은 요청 트랜잭션**에서 실행해
  실제 `planning.requirement` UUID를 만든다. `start_run`의 `input_snapshot`에 조건 스냅샷과
  requirement id 목록을 같이 남긴다.
- 이전에는 category != "computer"면 `NotImplementedError`(사실상 501)이었다 — 이제 baby가
  실제로 실행된다. computer 분기는 한 줄도 바뀌지 않았다(순수 함수 재사용 경계 보존).

### 2. `_execute_baby_recommendation` (백그라운드 태스크, 자체 커넥션)

- `load_persisted_baby_requirements`(DB 읽기)로 1단계에서 만든 requirement를 다시 읽는다
  (재계산 아님). `get_baby_candidates`(DB 읽기, 임베딩 없음)로 후보를 모은다.
- 후보마다 **실제 `engine.recommendation_candidate` 행을 먼저 만들고**(카탈로그
  offer_observation_id가 아니라 이 행의 진짜 UUID를 `BabyCandidate.candidate_id`로
  바꿔치기), 그 실제 run-스코프 행 위에서만 `verify_and_persist_baby_candidate`(P3, 실제
  RAG 검증+`persist_candidate_check`)를 호출한다 — 이래야 `persist_candidate_check`의
  "이 run에 속한 실제 candidate 행" 전제가 성립한다.
- `explain_baby_candidate`(P3)로 만든 설명을 `recommendation_candidate.reason`에 저장한다
  (`erepo.set_candidate_reason`, 새 메서드).
- `run_baby_optimizer`(P4, 순수 함수·DB/RAG 미호출)로 `BasketDecision`을 계산한 뒤,
  선택된 항목은 `engine.recommendation_candidate.result='selected'`로, 나머지는
  `'rejected'`로 갱신한다(새 CHECK 제약 `score IS NULL OR score_method_version IS NOT NULL`을
  맞추려고 `score_method_version="baby-optimizer-v1"`도 같이 쓴다).
- `BasketItem`을 실제 `planning.item` 행으로 영속화한다(`PlanRepo.upsert_basket_item`,
  새 메서드) — owned 항목은 `persist_baby_requirements`가 이미 만든 진짜
  `fulfilled_by_item_id`를 그대로 쓰고, to_purchase 항목만 새로 쓴다. 재추천마다
  `delete_purchase_items`로 이전 run의 to_purchase 행을 지운 뒤 다시 쌓는다(중복 방지).
- 실제 계산 결과로 `explanation_headline`/`explanation_text`/`reasoning_log`를
  `erepo.set_explanation`에 저장한다 — "영원히 pending" 없음.
- `feedback_service.emit_shown`(새 모듈)으로 `recommendation_shown` 이벤트를 run당 1회만
  남긴다(기존 `engine.feedback_event.event_key` UNIQUE 제약을 멱등키로 재사용, 새 테이블 없음).

### 3. `get_stored_result` baby 분기 — GET은 재계산하지 않는다

- `_load_baby_basket_items`가 저장된 `planning.item` 행을 `BasketItem`/`CandidateCheck`
  모양으로 되읽고, `_baby_items_and_totals`가 P4의 **순수 함수** `recalculate_basket`만
  호출해 총액/feasible/missing_requirements를 다시 계산한다 — DB 읽기 이상의 어떤
  검색·임베딩도 하지 않는다(RH02가 `get_embedder`/`RagService.search`를 raise하도록
  monkeypatch해서 실측 확인).
- 소유 항목은 `reason`/`checks`를 `ready`로 종결한다(전에는 owned 항목이 영원히
  `checks:pending`으로 남아 프론트 폴링(`tfResultPending`)이 끝나지 않는 버그가 있었다 —
  이번에 고쳤다).

### 4. PATCH/대안/교체/결과-메시지 (`src/routers/session.py`, `recommendation_service.py`)

- `PATCH .../items/{item_id}`, `GET .../items/{item_id}/alternatives`,
  `POST .../items/{item_id}/swap`, `POST /session/{id}/result-message` 4개를 새로 구현했다.
- 모두 `session_service.load_owned_draft`로 소유권을 확인하고, PATCH/swap은
  `If-Match` 헤더(=`lock_version`)를 요구한다 — 없으면 422, 최신과 다르면 409(
  `PlanRepo.bump_lock_version`이 조건 변경과 같은 `plan_revision.lock_version` 카운터를
  재사용한다).
- swap은 클라이언트가 보낸 candidate_id를 그대로 믿지 않는다 — `engine.recommendation_candidate`에서
  같은 run/같은 requirement에 속하는지, `get_candidate_eligibility`(새 메서드, `validation_result.issues`
  jsonb에서 적합성을 재구성)로 실제 선택 가능한지 확인한 뒤에만 가격/오퍼를 DB에서
  다시 채운다. 위조 후보는 422로 거부(RH03에서 실측).
- `result-message`는 LLM 없이 "슬롯 이름 + 싼/저렴 + 바꿔/교체" 패턴 하나만 이해한다.
  못 알아들으면 아무것도 바꾸지 않고 안내 문장만 돌려준다(RH06에서 실측).

## 왜 `complete`가 아니라 `partial`인가

1. **RH07이 이 환경에서 구조적으로 검증 불가능하다.** 브라우저 테스트 러너(Playwright 등)가
   설치돼 있지 않고, 저장소에 프론트엔드 E2E용 `package.json`도 없다. EXIT 조건이 명시하듯
   이는 그 자체로 `complete`를 막는 정확한 차단 사유이며, 가짜로 만들지 않았다.
2. **RH05가 검증하는 "편집 메커니즘 자체"는 실 DB로 통과했지만, 그 편집 대상이 되는
   "실제로 selection_allowed=True인 to_purchase 후보"는 이 시드 카탈로그+현재 리뷰된
   규칙 인벤토리(`MANUAL_RULE_INVENTORY={stroller only}`, P2/P3 산출물, 이 작업이
   만들지 않음)에서 자연 발생하지 않는다.** '외출' need는 항상 car_seat를 mandatory-now로
   끌고 오는데 시드된 3개 car_seat 변형 모두 KC 인증이 `unknown`이라 전부
   `selection_allowed=False`이고, P4의 "필수 항목 전부 안 되면 하나도 확정 안 함" 설계상
   stroller(그 자체는 적합 판정을 받음)까지 구매 후보에서 제외된다. 이는 이 작업이 만든
   버그가 아니라 P2/P3/P8 단계의 카탈로그·규칙 커버리지가 아직 얕다는 사실을 보여주는
   실측이다 — RH05 테스트는 프로덕션과 동일한 `persist_candidate_check` 경로로 "P3가
   승인했다면 만들었을" to_purchase 행 하나를 실 DB에 추가해 편집/교체/동시성 로직
   자체를 검증했다(모듈 docstring에 이유를 명시).
3. **동시성 완전 직렬화(part unique index)·프로세스 재시작 후 abandoned run 회수**는
   설계는 반영했지만(요청 트랜잭션 내 체크, `complete_run`의 lock_version 비교) 스키마
   변경(부분 유니크 인덱스)이나 별도 회수 워커까지는 이 작업 범위에서 구현하지 않았다 —
   `remaining`에 정확히 남은 조건을 적었다.
