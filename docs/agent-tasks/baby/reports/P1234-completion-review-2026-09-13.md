## 완료를 막는 결함

### R1 — P1: 대표 월령이 정확한 월령으로 바뀜 (높음, 기존 재현 재사용)

`src/services/session_service.py:403–406`의 `_current_values()`가 조건 JSON에서 value만 꺼내 exact=False를 잃는다. `normalize_baby_conditions()`(61행)가 정수를 정확값으로 해석하므로 대표값5개월이 exact=True가 된다. P012 검토의 실제 DB 재현과 P2/P3 최신 보고서의 미해결 표기가 일치하고 현재 코드도 동일하다. 기존 테스트를 다시 돌리지 않았다.

**영향:** 사용자가 정확한 나이를 주지 않았는데 안전 규칙에 정확값으로 전달될 수 있다. P3가 exact=False를 올바르게 취급해도 upstream에서 True가 되면 보호하지 못한다.

**재승인 조건:** JSON 메타데이터를 보존하는 공통 정규화 입력 계약으로 변경하고 칩→저장→공식 정규화→P3의 흐름에서 exact=False 유지 증명. P1 보고서에 남은 HTTPS Secure 쿠키 설정/검증도 별도로 정리한다.

### R2 — P2/P4: 부분 보유품의 같은 ID 때문에 구매 필요분까지 보유로 판정 (높음, 신규 통합 확인)

`src/engine/stage2_requirement.py:259–280`은 소유 조각과 잔여 조각을 같은 planning.requirement.id로 반환한다. `src/engine/stage4_optimize.py:149–163`은 fulfilled_by_item_id가 있는 조각의 **id 집합**으로 두 조각 모두를 보유로 처리한다.

실제 규칙의 수유/젖병 필요2개·보유1개를 사용했다. 별도 DB `p0_fix_20260913`에 세션과 필요 품목을 저장한 후 P4에 넘겼다. 반환된 두 requirement는 같은 UUID이고 한쪽만 실제 fulfilled_by_item_id가 있다. 그런데 후보가 전혀 없는 상황에서도 P4는 owned1개짜리 행2개, selected_price=0, missing_requirements=[], feasible=True를 반환했다. 모든 SQL은 rollback했다. 보고서의 유모차 필요1개·보유1개 통합 사례로는 드러나지 않는 경계다.

**재승인 조건:** 한 requirement에 총 필요량과 실제 충족량을 표현하거나, 소유/잔여 조각에 충돌 없는 실제 식별자를 부여하는 단일 계약으로 P2 저장·재조회·P4를 함께 수정한다. 필요2/보유1/후보없음→구매 필요1개·불가능, 후보있음→정확히1개만 구매, 다시 읽어도 동일 결과를 확인한다. P4만 임시로 ID 비교를 피하는 것으로 P2 반환 계약 문제를 숨기지 않는다.

### R3 — P3: 인증 정보가 완전히 없으면 unknown이 아닌 pass (높음, 신규 경계 확인)

`src/engine/stage3c_verify.py:159`는 kc_certification_number 항목이 **존재하고** verification_status가 unknown인 경우만 막는다. facts={}인 car_seat 후보는 `src/rag/verification.py:17`의 고정 REVIEWED_NOT_APPLICABLE 목록을 거쳐 pass/selection_allowed=True가 된다. 실측 coverage=none, verification=unknown이고 이유는 no_manual_safety_condition_documented다. P3 VE03 기존 검증은 명시적인 unknown 사실을 가진 픽스처이며 사실 자체가 빠진 경우와 다르다.

이는 법률상 인증 대상을 새로 판단한 것이 아니라 지시서의 “필수 사실 누락→unknown”, “규칙 없음과 검토된 무해당 구분”을 검토한 결과다. 다른 품목의 실제 안전 기준을 이번에 만들어 넣지 않는다.

**재승인 조건:** 검토된 제품군별 적용 규칙·버전·근거를 기준으로 인증 사실의 없음/미확인/충돌/검증됨/무해당을 구분한다. 확인된 무해당 근거 없이 자료가 없다는 이유만으로 pass시키지 않는다. 누락 사실 및 미검토 품목→자동선택 불가를 검증한다.

### R4 — P4: 편집 재계산에서 후보 검증과 단위 일치 검사 누락 (높음, 신규 경계 확인)

`src/engine/stage4_optimize.py:353`은 candidate_id가 있을 때만 CandidateCheck를 찾는다. candidate_id=None·checks=[]인 구매 선택 행도 selected=True, feasible=True다. 또한373–379행은 item.qty를 단위 비교 없이 더하므로 필요 단위each에 보유 단위kg를 넣어도 충족/feasible=True다.

두 경우 모두 공개 DTO가 허용하는 입력으로 순수 경계 함수를 직접 호출해 확인했다. P5가 가격을 권위 있는 값으로 공급해야 한다는 조건과 별개로 P4의 안정 식별자·허용 판정·단위 검증 책임은 남는다. 기존 OP08은 최초 optimize의 보유 매칭 단위만 검사하고 recalculate의 단위 불일치는 검사하지 않는다.

**재승인 조건:** 선택된 구매 행에 올바른 후보·판정·요구사항 연결을 필수화하고, 최초 계산과 편집 재계산에서 동일한 단위/수량 규칙을 적용한다. 검증 누락·타 요구사항 후보·단위 불일치가 미충족으로 남아야 한다.
