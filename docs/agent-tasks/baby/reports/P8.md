## 평가 (`scripts/evaluate_review_signals.py`)

승인 라벨만 정답으로 쓰고, leakage 단위(리뷰어→부모 표본→상품 순)가 서로 다른 split에
걸치면 평가를 거부한다. 클래스별 독립 leakage 단위가 5개 미만이면 confusion matrix 대신
`not_evaluated` + 정확한 사유·문턱·실제 수를 낸다. 커밋된 고정 픽스처(3개 표본, 양성 1/음성
2 leakage 단위)로 실행하면 실제로 `not_evaluated`가 나온다 — 이는 버그가 아니라 설계된
동작이다(표본이 이 정도로 적을 때 confusion matrix를 내면 숫자는 그럴듯해 보이지만 아무
것도 검증하지 않는다). **이 저장소에는 실제 탐지 성능을 주장할 수 있는 실측 라벨 코퍼스가
없다** — 더 큰 승인 라벨 세트가 확보되기 전까지 어떤 정확도 수치도 내지 않는다.

## FB01/FB02 — 내부 append-only 헬퍼

`feedback_service.emit()`에 payload whitelist(`_validate_payload`)를 추가했다: 키는
`*_id` 패턴이거나 `{action,version,reason_code,source}` 중 하나여야 하고, 값은 스칼라만
허용한다(중첩 dict/list 거부) — email/note/token 같은 임의 필드는 `ValueError`로 즉시
거부되고 부분 행도 남지 않는다. 기존 호출부(`recommendation_service.py`,
`list_service.py`)는 전부 `payload` 인자를 안 쓰므로 이 추가로 깨진 기존 동작은 없다
(실 DB로 재확인). 기존 `event_key` UNIQUE + `ON CONFLICT DO NOTHING`이 이미 중복 억제와
"재전송해도 원본 행이 안 바뀜"을 보장하는 것을 실 DB 트랜잭션으로 확인했다(FB01/FB02).
`stage6_feedback.run_batch()`는 여전히 `NotImplementedError` — 자동 재학습 잡은 없다.

## FB03 — 완료

네 액션 전부 실제 실행 경로에 배선되고 실 DB+실 HTTP로 검증됐다:

- **shown**: `execute_recommendation`의 컴퓨터 경로, `complete_run` 직후(같은 트랜잭션).
  event_key가 `run_id`를 포함해 재실행마다 새 이벤트가 되고, GET/폴링을 몇 번 반복해도
  중복되지 않는다.
- **replaced**: `swap_item`이 실제로 `update_candidate_variant`를 성공시킨 뒤에만 기록.
  존재하지 않는 후보로의 교체 시도(404)는 아무 것도 남기지 않는다.
- **removed**: `patch_item`이 `selected: true→false` 전환일 때만 기록(수량/시점만 바꾸는
  patch나 이미 선택 해제된 항목을 다시 해제하는 요청은 기록하지 않는다). 재선택 후 같은
  버전에서 다시 해제해도 event_key가 버전 스코프라 중복 기록되지 않는다.
- **confirmed**: `list_service.confirm()`이 draft→confirmed 전환(및 구매 항목 동결)에
  성공한 뒤에만 기록. 이미 확정된 목록에 대한 재확정 시도는 `confirm_revision`의 원자적
  UPDATE가 먼저 `Conflict`(409)로 막아 아무 것도 남기지 않는다.

`tests/test_feedback_events.py`의 컴퓨터 카테고리 실 HTTP 플로우(추천 202+폴링 → 대안
조회+교체 → 항목 제외 → 로그인+확정)로 위 전부를 확인했다(FB03 관련 6건 + FB01/FB02
9건 = 15건).
