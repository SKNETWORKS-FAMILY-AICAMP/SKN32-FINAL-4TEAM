# P0·P1·P2 결과 검토 (2026-09-13)

## 판정

**세 작업 모두 changes_required.** P0 v4(0013 포함), P1 조건 대화, P2 카탈로그/규칙을 현재 작업 트리 기준으로 검토했다. 앞서 검토한 P0 v3의 JSON/도메인 개선은 최신0013에서 반영됐으므로 동일 결함으로 재지적하지 않는다. 구 데이터 이관은 사용자 결정에 따라 승인 조건에서 제외한다.

|---|---|---|
| P0 | 새 스키마 설치, JSON 근거 검사, 후보 revision 연결, 도메인 스냅샷 저장, 실 DB 테스트 | planning.item 및 fulfilled_by_item_id의 참조·소속 제약 누락 |

P1/P2 작업을 폐기하거나 처음부터 다시 만들 필요는 없다. 아래 오류를 해당 작업에서 보완한다. 세 작업을 완료로 표시하거나 이 출력에 의존하는 P3/P4/P5 통합 완료를 선언하기에는 이르다. Baby 추천501 및 후기 업무 미구현은 각각 P5/P8 범위이므로 이번 결함으로 계산하지 않았다.

## 검토 결과 (중요도순)

### R1 — P0: 없는 목록·상품·보유품을 참조하는 데이터가 저장됨

근거: `db/migrations/0010_schema_reduction_v1.sql:22` planning.item 정의에는 revision_id/variant_id 등의 FK가 없고, 0012/0013도 이를 완성하지 않는다. requirement.fulfilled_by_item_id 역시 무결성 검사가 없다.

실 SQL에서 무작위 UUID를 revision_id/variant_id로 넣은 owned item INSERT가 성공했다. 실제 requirement의 fulfilled_by_item_id를 존재하지 않는 UUID로 UPDATE해도 성공했다. 모두 검토용 트랜잭션에서 rollback했다. P0 SR08의 없는 ID/다른 revision 참조 거부 요구를 충족하지 않는다.

수정: item의 실제 FK(variant/offer/observation/revision), 충족 item 존재 및 동일 revision 소속을 강제한다. 없는 ID와 타 revision의 실제 item을 각각 거부하는 SQL 테스트를 추가한다. 단순히 DTO 타입만 UUID로 바꾸면 해결되지 않는다. 다음 전진 마이그레이션 사용.

### R2 — P1: 구간 월령이 정규화 후 정확 월령으로 바뀜

근거: `src/services/session_service.py:403`의 _current_values는 JSON의 value만 꺼내 exact를 버린다. 같은 파일:61 normalize_baby_conditions는 이 반환값을 받도록 문서화돼 있고, 정수값을 exact=true로 간주한다.

실제 q_age=[5] 저장 결과는 `{value:5,exact:false}`인데 _current_values → normalize 결과는 `{months:5,exact:true}`다. 화면에서는 추정 연령으로 표시해도 후속 검사에서는 정확한5개월로 오인할 수 있다.

수정: DB에서 정규화까지 exact/range/missing 정보를 보존하는 하나의 타입을 사용한다. 실제 q_age 칩 입력→저장→정규화→P2/P3 전달까지 exact=false를 유지하는 연결 테스트가 필요하다.

### R3 — P1/P2: 공개된 정규화 결과를 규칙 함수가 받지 못함

근거: session_service:71은 age_stage.months를 반환하고, `src/engine/stage2_requirement.py:98`은 최상위 age_months를 읽는다. P2 테스트는 P1 출력 대신 직접 만든 age_months dict를 사용한다.

정확8개월/수유 조건을 normalize_baby_conditions에 넣고 결과를 build_baby_requirements에 넘기면 `feeding_bottle_v1: mode=born 인데 age_months 없음`이 발생한다. reference_date를 제공해도 발생한다.

수정: 공통 NormalizedConditions 계약에 맞춰 생산자/소비자를 정렬하거나 명시적 공통 어댑터를 제공한다. revision_id 및 reference_date의 제공 위치도 함께 명시한다. born/prenatal, 정확/구간 월령의 실제 연결 테스트를 추가한다. P5가 임의의 필드 변환을 다시 작성하도록 넘기지 않는다.

### R4 — P2: 포장당 수량40이 후보에서1로 손실됨

근거: `scripts/seed_baby_catalog.py:149` 이후 저장 경로는 입력 unit_qty를 저장하지 않는다. `src/engine/stage3_0_candidates.py:65`는 unit_qty=1을 고정한다.

실제 SYN-DIAPER-CA03-001 fixture의 unit_qty=40을 적재·조회하면 BabyCandidate.unit_qty=1.0이다. 입력 JSON만 검사하는 CA03 테스트로는 놓친다. P4의 필요한 수량·묶음 수 계산 입력이 잘못된다.

수정: unit_qty를 옵션에 저장하고 조회/DTO까지 그대로 전달한다. pack_quantity, 구매 qty, unit_qty의 의미를 분리하여 2팩×40개가80개이고 가격은2팩 기준인 연결 테스트를 추가한다.

### R5 — P2: 보유품 저장 요구를 후속 작업으로 잘못 넘김

근거: `src/engine/stage2_requirement.py:138`은 fulfilled_by_item_id에 UUID 대신 `owned:유모차`를 반환한다. P2 보고서는 영속화를 P1/P4로 넘기지만, P2 지시서 IMPLEMENTATION5는 별도 repository operation으로 planning.item과 requirement 연결을 저장하도록 명시한다.

실제 함수 결과도 `owned:유모차`다. 이는 DB uuid 필드에 직접 저장할 수 없고, 실제 보유 item 존재/소속 증거도 아니다.

수정: 순수 함수는 보유품 의도/미해결 참조를 별도 필드로 반환하고, P2 저장 연산이 실제 UUID를 발급·조회해 requirement와 연결한다. 멱등 저장·부분 수량 분할·같은 revision 소속을 실제 SQL로 검증한다. P0 R1 제약 보완과 맞춰 진행한다.

### R6 — P2: 실행 규칙이 입력 스냅샷에 고정되지 않음

근거: `src/engine/stage2_requirement.py:89`는 _load_rules()로 현재 YAML을 읽으며 domain_snapshot에서는 reference_date만 사용한다. 실제 적용된 전체 규칙/해시를 스냅샷에서 읽거나 결과에 고정하지 않는다.

코드 검토상 같은 조건과 같은 스냅샷이어도 배포 후 프로세스가 새 YAML을 읽으면 결과가 바뀔 수 있다. 현재 테스트의 연속2회 호출은 동일한 캐시를 쓰므로 배포/규칙 변경을 검증하지 않는다.

수정: P2 규칙 내용·버전·hash를 실행 스냅샷에 포함하고 그 내용을 소비한다. 규칙 파일이 바뀌어도 이전 스냅샷 재계산은 같은 결과이며 신규 스냅샷만 새 규칙을 쓰는 테스트를 추가한다.
