- **R1 (보유 출처 UUID만 검사)**: `PlanRepo.active_condition`(신규)이 조건 id와 함께 실제 value를 반환한다. `persist_baby_requirements`가 이 value의 라벨 개수를 세어(`Counter`) 각 owned entry의 qty가 그 한도를 넘으면 거부하고(`owned_qty_exceeds_reported`), 이번 호출 안의 모든 requirement에 걸쳐 라벨별 누적 배분량을 추적해 같은 실제 물품이 두 슬롯에 중복 배분되는 것도 막는다.
- **R2 (동시 생성 직렬화 없음)**: `PlanRepo.lock_revision`(공개 래퍼) 을 `persist_baby_requirements` 시작 지점에서 호출해 조건 쓰기와 동일하게 리비전 단위로 직렬화한다. 중복 검사를 `DTO.id` 외에 `slot_key`로도 하도록 강화했다.
- **R3 (사라진 슬롯이 계속 active로 남음)**: `PlanRepo.exclude_requirements_not_in(revision_id, keep_slot_keys)`(신규)이 이번 계산에 없는 baby requirement를 `status='excluded'`로 전환한다. `ensure_requirement`/`set_requirement_totals`는 되살아난 슬롯을 `status='active'`로 되돌린다(같은 UUID 재사용).
- **R4 (match_spec 덮어쓰기·JSON 신뢰)**: 기존 requirement가 있으면 `ensure_requirement(...,{})`로 지웠다 다시 쓰는 대신 `PlanRepo.get_requirement_by_node`(신규)로 기존 match_spec을 먼저 읽어 `baby_requirement` 키만 갱신한다. `load_persisted_baby_requirements`는 `id`/`revision_id`/`slot_key`를 JSON 복사본이 아니라 실제 관계 컬럼(`req.id`/`req.revision_id`/`n.template_key`)에서 복원한다.
- **R5 (명시적 보유 수량 미연결)**: `build_baby_requirements`가 `set(owned_items)` 대신 `Counter`로 라벨 등장 횟수를 세어, 소유 개수 N에 대해 `min(N, required_qty)`를 인정한다(P1 review R2와 짝: 반복된 라벨이 수량이다).
