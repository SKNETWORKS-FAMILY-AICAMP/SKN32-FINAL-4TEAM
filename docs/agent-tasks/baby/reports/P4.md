# P4 실행 보고 — 필수품·예산·구매 시점 최적화

## 실제로 구현한 것

CONTRACTS.md와 `reports/sync-2026-09-13.md`의 델타 지시대로 P0(축소 스키마)·P2(유아
카탈로그·요구사항 규칙)·P3(후보 검증)를 코드로 재확인한 뒤, 그 산출물 타입
(`BabyRequirement`/`BabyCandidate`/`CandidateCheck`) 위에 이 과업의 세 경계 함수를
구현했다:

```python
rank_baby_candidates(requirements, candidates, checks, profile) -> RankedCandidates
optimize_baby(requirements, ranked, owned_items, budget_max) -> BasketDecision
recalculate_basket(items, requirements, budget_max, checks) -> BasketDecision
```

### 1. `rank_baby_candidates` (`src/engine/stage3b_rank.py`)

- ALGORITHM 1단계 검증을 실제로 수행한다: 정수 KRW 가격(`invalid_price`),
  양수 `pack_quantity`/`unit_qty`(`invalid_pack_quantity`/`invalid_unit_qty`),
  안정 식별자(`missing_product_key`), 그리고 대응하는 `CandidateCheck` 존재
  여부(`missing_candidate_check`) — 실패하면 `RankedCandidates.excluded`에 이유와
  함께 기록하고 조용히 버리지 않는다.
- PC의 고정 리뷰=0.5·고정 기여도를 재사용하지 않는다. `config/baby_optimizer_profile.yaml`이
  버전이 매겨진 가중치(price/review)를 데이터로 갖고, `review_summary.avg_rating`이
  없으면 그 후보의 가중 평균에서 리뷰 축과 그 가중치를 통째로 제외한다(0.5로
  채우지 않음) — `test_rank_absent_review_excluded_from_weighted_average_not_fabricated`로
  검증.
- 결정적 동점 처리: `(price, product_key, variant_key)` 튜플로 정렬 — 재현 가능.
- `eligibility=fail`/`unknown`인 후보도 순위에는 남는다(진단 가시성, CONTRACTS
  "retain visible diagnostic candidate") — 다만 `selection_allowed=False`로
  자동 선택은 막는다. `optimize_baby`가 이 플래그로 필터링한다.

### 2. `optimize_baby` (`src/engine/stage4_optimize.py`)

- **소유 수량 처리(2단계)**: 두 가지 실제 입력 경로를 모두 처리한다 — (a) P2의
  `build_baby_requirements`가 이미 쪼갠 소유 조각(`fulfilled_by_item_id` 설정됨,
  required_qty가 곧 소유량)은 그대로 `status=owned`로 옮긴다, (b) 별도로 전달된
  `owned_items`(원 물리 재고)는 slot_key+unit_code가 정확히 일치하는, 아직
  `fulfilled_by_item_id`가 없는 요구사항에만 매칭한다 — 같은 물리 수량이 두 경로
  모두에서 이중 차감되지 않는다.
- **필수 항목 완전탐색(4단계)**: 지금(now) 시점 필수 요구사항마다 유효 후보 목록에
  대해 하한(가장 싼 유효 조합 합)을 이용한 가지치기 완전탐색(branch-and-bound)을
  수행한다. 목적함수는 사전식(lexicographic) — 전부 충족 → 구성된 효용(score) 합
  최대화 → 가격/키 동점 처리. 8개 무작위 시드에 대해 완전탐색(brute-force)
  오라클과 결과가 일치함을 `test_branch_and_bound_matches_brute_force_oracle_on_tiny_random_cases`로
  확인했다.
- **불가능 시(5단계)**: 자동으로 나중으로 미루지 않는다 — `missing_requirements`에
  각 필수 요구사항의 `required_qty`/`cheapest_feasible_subtotal`을 채우고,
  하나라도 선택 가능한 후보가 없으면(`no_selectable_candidate`) 전체
  `cheapest_feasible_subtotal`/`budget_shortfall`을 `None`(모름)으로 둔다 — 0으로
  채우지 않는다.
- **선택 항목(6단계)**: optional-now는 필수 항목이 다 쓰고 남은 예산 안에서만
  욕심 알고리즘으로 추가한다(효용 내림차순 → 동점 처리); soon/later는
  `soon_price`/`later_price`로 따로 보고하고 지금 예산을 절대 쓰지 않는다.
- 팩 수량 버그 재현 방지(OP04): `unit_price × qty`만 청구 총액에 들어가고,
  `qty × unit_qty`는 별도로 `selected_units`에만 들어간다 — 곱해서 800,000원이
  되는 대신 20,000원/80개로 정확히 분리됨을 실측 확인.

### 3. `recalculate_basket` (`src/engine/stage4_optimize.py`)

- 클라이언트가 보낸 price/unit_qty/review/check를 신뢰하지 않는다 — `items`는
  이미 P5가 후보 원장에서 다시 채운 권위 있는 `unit_price`/`unit_qty`를 담고
  있다고 가정하고, 이 함수는 그 값의 정합성(qty>0, price>=0, `selection_allowed`)만
  재검증한다.
- 필수-지금 항목의 시점을 later로 명시적으로 바꾸면, 예산이 충분해도 해당
  요구사항이 `missing_requirements`에 다시 나타나 `feasible=False`가 된다
  (ALGORITHM 6단계) — `test_op07_explicit_timing_change_of_mandatory_now_blocks_confirmation_even_if_budget_fits`.

### 4. `src/pipeline.run_baby_optimizer` (baby computation boundary)

## 왜 `complete`가 아니라 `partial`인가

CONTRACTS의 종료 조건 원칙(P0-P3 보고서와 동일)에 따라 이 보고서가 스스로
`complete`를 선언하지 않는다. 정직하게 남는 경계는 위 `remaining` 블록과 같다 —
요약하면: (1) `execute_recommendation()`/HTTP 배선은 CONTRACTS가 명시한 대로 P5
소관이라 이 과업 범위 밖이다(baby POST recommend는 여전히 501, 이 과업이 바꾸지
