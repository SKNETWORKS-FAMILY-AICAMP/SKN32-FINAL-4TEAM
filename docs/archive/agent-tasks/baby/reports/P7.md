# P7 v3 — develop `da79839` purchase-line confirmation

The implementation keeps develop's `planning.purchase_line`, `planning.plan_node`,
`planning.requirement`, and `engine.recommendation_candidate` schema. It does not
restore `planning.item`, removed ownership tables, a PostgreSQL `rag` schema, or old
reduction SQL.

`POST /lists/{id}/confirm` now requires `If-Match` for a draft, locks revision and
completed run, writes selected candidates using their persisted `qty` as
`pack_count`, stores `unit_price * qty` as `line_amount`, checks offer/observation/
variant ownership and valid available observations, and separates `now`, `soon`, and
`later` totals. Baby candidates additionally require a persisted pass verdict.
The same transaction appends `baby_confirmation` version 3 to the completed run's
existing input snapshot and emits an idempotent `plan_confirmed` feedback event.
Repeat confirmation returns existing snapshots without another insert. Reports read
only revision and purchase-line/run snapshots.

- **R2 (최신 조건/추천 결과 일치 확인 없음)**: `confirm()`이 이제 (1) revision의 **가장 최근 run**(상태 무관)이 `completed`가 아니면 거부하고(더 이상 "가장 최근 completed"만 보지 않음), (2) 지금의 실제 조건 값을 `start_recommendation`과 같은 방식으로 재구성해 그 run의 `input_snapshot.values`와 다르면 거부한다(`stale_recommendation`) — 단순 `lock_version` 비교는 후보 편집만으로도 값이 늘어나 오탐이 생기므로 쓰지 않았다.
- **R3 (화면에서 If-Match 미전송)**: `frontend/js/core.js`의 `TF_PLAN.confirm`이 `updateItem`/`swap`과 같은 방식으로 `If-Match` 헤더를 보낸다. 백엔드는 P0.md에서 이미 고친 대로 잘못된 헤더를 422로 명시 처리한다.
- **R4 (보유 snapshot·팩 단위 정보 불완전)**: `baby_confirmation.owned`는 이제 확정 시점의 전체 requirement 집합(`load_persisted_baby_requirements`)에서 `(requirement_id, source_condition_id)` 기준으로 중복 제거해 만든다 — 과거엔 구매 snapshot에 없는 `'owned'` 키를 찾던 코드라 항상 빈 배열이었다. purchase snapshot의 `unit_qty`는 실제 `catalog.product_variant.pack_quantity`를 쓴다(과거엔 1 고정). `_report`가 `owned`를 응답에 포함하도록 `schemas.ReportOut`에 필드를 추가했다.
- **R5 (저장된 pass만 확인, 현재 근거 유효성 재검사 없음)**: 선택된 baby candidate의 안전 판정이 `pass`인 issue마다, 그 issue가 인용한 evidence_refs 각각을 지금 다시 확인한다 — `evidence.evidence.status`가 여전히 `active`인지, 그 material_revision이 지금도 `is_currently_published`인지, `material_applicability`가 지금도 이 candidate의 실제 product/variant에 verified로 걸려 있는지(P3에서 만든 `MaterialRepo.has_current_applicability` 재사용). 전부 로컬 DB 조회이며 트랜잭션 안에서 RAG/임베딩 호출은 하지 않는다.
