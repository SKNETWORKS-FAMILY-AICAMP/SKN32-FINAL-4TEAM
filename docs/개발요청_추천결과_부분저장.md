# 개발 요청 — 추천 결과 부분 저장 (문장 필드 pending/ready 분리)

**요청 대상:** `develop` 소유 파일(`src/services/recommendation_service.py`, `src/repo/engine_repo.py`) 담당자.
**요청자:** sllm 브랜치([3-C]·[5] LLM 연동 담당).
**기준일:** 2026-09-13.

## 한 줄 요약

`execute_recommendation`이 [2]~[5]를 전부 끝내야 `run.status`를 `completed`로 바꾼다. [5]가 규칙
템플릿이던 어제까지는 문제가 안 됐는데, 오늘부터 [3-C]·[5]가 실제 OpenAI를 호출하면서 부품·가격·
검증은 이미 끝났는데도 문장 하나 때문에 사용자가 계속 로딩 화면을 본다. LLM 호출이 실패하면
추천 전체가 `failed`로 떨어질 위험도 있다. **부품표가 나오는 즉시 저장·`done` 처리하고, 문장은
나중에 `pending → ready/failed`로 채우자.**

## 현재 코드가 실제로 하는 일

`execute_recommendation`([recommendation_service.py:75-177](../src/services/recommendation_service.py#L75-L177))이
한 트랜잭션 흐름 안에서 순서대로 실행한다:

```
[2] stage2_requirement   → 요구사항 확정
[3-A] stage3a_hardfilter → 후보 필터
[3-B] stage3b_rank       → 순위
[4] stage4_optimize      → 세트 확정 (부품·가격 여기서 끝)
[3-C] stage3c_verify     → 검증 (LLM 호출, verify_build 내부)
[5] stage5_explain       → 설명 문장 (LLM 호출) ← reason_by_slot도 여기서 나옴 (L114)
  ↓
add_candidate × N (L115-124)   — item별 reason을 이 시점에 같이 저장
add_validation × N (L126-134)
set_explanation (L163-168)      — headline/text/reasoning_log 저장
complete_run (L169)             — 여기서만 status가 running → completed
```

`get_stored_result`([recommendation_service.py:218-307](../src/services/recommendation_service.py#L218-L307))는
`run.status`가 `running`이면 items를 아예 안 채우고 즉시 반환한다(L257-258). 즉 [5]가 안 끝나면
프론트는 부품표를 한 줄도 못 본다.

**LLM 실패 처리도 전체 단위다.** L170-177의 `except Exception`은 `execute_recommendation` 함수
전체를 감싸므로, [5]의 OpenAI 호출이 예외를 던지면 이미 확정된 부품·가격·검증까지 통째로
`failed`로 처리된다.

## 계약은 이미 이 상황을 가정하고 있다

`TextStatusOut`(`src/schemas.py:154`)과 `ItemOut.reason`/`ItemOut.checks`(`src/schemas.py:196-197`)는
`{"status": "pending"|"ready"|"failed", "text": ...}` 모양이고, 프론트는 `pending`이 하나라도 남아
있으면 폴링을 계속하도록 이미 구현돼 있다(계약 §D-4-0). `get_stored_result`도 이미 이 모양을
일부 반영한다 — `explanation` 필드는 `run.explanation_status`를 보고 `ready`/`pending`을 가른다
(L302-306). **문제는 `run.status` 자체(=`done` 여부)가 아직 이 세분화를 안 따라간다는 것.**

`engine_repo.set_explanation`(L34-41)도 이미 `run.status`를 건드리지 않는다 — `explanation_*`
칼럼만 갱신한다. `complete_run`(L13-20)은 `run.status`가 `running`일 때만 동작한다는 제약이
있을 뿐, `set_explanation`보다 먼저 불러도 되는 순서상 제약은 코드에 없다. 즉 **`complete_run`을
[5] 이전으로 옮기는 것 자체는 지금 스키마·리포 메서드로 이미 가능**해 보인다 — 다만 아래 두
가지는 새로 필요하다.

## 요청하는 변경

### 1. `execute_recommendation`의 실행 순서 재배치

```
[2] → [3-A] → [3-B] → [4] → [3-C]
  ↓
add_candidate × N  (reason=None으로 저장 → add_candidate가 자동으로 reason_status='pending' 처리, L22)
add_validation × N
complete_run(run_id)          ← 여기로 앞당김: 부품표 확정 시점에 바로 done
  ↓
try: stage5_explain 실행 (LLM 호출)
    성공 → 아래 "2." 로 item별 reason 갱신 + set_explanation 호출
    실패 → explanation_status='failed'로 표시 (아래 "3." 참고), run.status는 건드리지 않음
```

`add_candidate`는 이미 `reason=None`이면 `reason_status='pending'`을 자동으로 넣는다(L22) —
지금 코드가 안 쓰고 있을 뿐 이미 있는 기능이다.

### 2. item별 `reason`을 나중에 채울 리포 메서드 필요

지금은 `reason_by_slot`이 `stage5_explain.run()`의 결과에서 나오고(L112, L114), `add_candidate`
호출 시점(L120-124)에 같이 박힌다. 순서를 바꾸면 후보 저장 시점엔 아직 `reason`이 없으므로,
LLM이 끝난 뒤 **후보 row를 찾아 reason만 UPDATE하는 메서드**가 `EngineRepo`에 새로 필요하다.
예: `update_candidate_reason(candidate_id, reason)` → `reason`, `reason_status='ready'` 갱신.
(어떤 후보인지 매칭은 `run_id` + `slot`으로 — `add_candidate` 때 넣은 `requirement_id`를
`req_id_by_slot`에서 이미 slot별로 들고 있으니 그대로 재사용 가능.)

### 3. `explanation_status='failed'` 갱신 메서드 필요

`set_explanation`(L34-41)은 성공 경로(`status='ready'`)만 있다. [5] LLM 호출이 실패했을 때
`explanation_status='failed'`로 남길 메서드(또는 `set_explanation`에 상태 파라미터 추가)가
필요하다. 프론트가 이 값을 "설명을 만들지 못했습니다" 같은 문구로 보여줄 수 있게.

이 실패는 **`execute_recommendation` 전체의 `except`(L170-177)에 걸리면 안 된다** — 지금처럼
전체를 실패로 떨어뜨리면 이미 저장된 부품·가격·검증까지 같이 죽는다. [5] 호출만 별도
try/except로 감싸야 한다.

## 참고 — [3-C]는 이미 부분적으로 이 원칙을 따른다

`src/CLAUDE.md`에 이미 명시돼 있듯 "[3-C] 문장 생성 실패는 신뢰도 점수에 영향을 주지 않는다"는
원칙이 있다. 이번 요청은 같은 원칙을 [5]에도 적용하고, `run.status` 자체의 전환 시점까지
맞추는 것이다.

## 영향 범위 (프론트가 체감하는 변화)

| | 지금 | 바뀐 뒤 |
| --- | --- | --- |
| 저장 시점 | [2]~[5] 전부 끝난 뒤 | 부품·가격·검증([2]~[4]+[3-C]) 끝나면 먼저 저장 |
| `run.status` → `done` | LLM 문장까지 끝나야 | 부품표 나오면 바로 |
| item `reason` | 처음부터 값 있음 | 처음엔 `pending` → 나중에 `ready`/`failed` |
| `explanation` | 처음부터 값 있음 | 처음엔 `pending` → 나중에 `ready`/`failed` |
| LLM 실패 시 | 추천 전체 `failed` 위험 | 부품표는 살아있고 문장만 `failed` |

API 응답 스키마(`schemas.py`)는 안 바꿔도 된다 — 이미 `pending`/`ready`/`failed` 세 상태를
받게 돼 있다. 프론트도 이미 `pending`이면 폴링을 유지하도록 구현돼 있다고 들었다(계약
§D-4-0 기준. 원문은 `origin/develop`/`origin/front`의 `docs/frontend_외부수정요청.md` 참고 —
이 브랜치 워킹트리에는 해당 파일이 삭제돼 없음).

## 왜 여기서 직접 안 고치고 요청으로 넘기나

`execute_recommendation`·`get_stored_result`·`EngineRepo`는 `src/CLAUDE.md`상 `develop` 소유다.
그리고 이 변경은 **"언제 `done`이 되는가"라는 계약상 겉으로 드러나는 동작**을 바꾸는 것이라,
혼자 고치면 develop 머지 때 되돌아갈 위험이 있다. 합의 후 develop 쪽에서 반영해 주면 sllm
쪽 [3-C]/[5] 코드는 그대로 맞춰 쓸 수 있다.

## 확인 요청 사항

1. 위 순서 재배치([2]~[4]+검증 → 저장 → `complete_run` → [5])에 동의하는지.
2. `update_candidate_reason` 같은 메서드를 `EngineRepo`에 추가하는 것을 누가 반영할지
   (develop 쪽에서 직접 추가 vs sllm 쪽에서 PR 제안).
3. `explanation_status='failed'` 갱신 방식 — 새 메서드 추가 vs `set_explanation`에 `status`
   파라미터 추가.
4. 테스트 기준선(`sllm` 기준 36 passed, develop 기준 96 passed)에 이 변경 반영 후 회귀 테스트
   범위.
