# P3 실행 보고 — 후보 안전 조건·설명서 검증·근거 연결

## 실제로 존재하는 것 (실측 근거 포함)

CONTRACTS.md와 `reports/sync-2026-09-13.md`의 델타 지시대로, P0(축소 스키마 위의 기존 RAG
동작 보존)와 P2(유아 카탈로그·요구사항 규칙)를 코드로 재확인한 뒤 그 위에 이 과업의
네 가지 경계 함수를 구현했다:

```python
verify_baby_candidate(rag_service, candidate, conditions, run_context) -> CandidateCheck
explain_baby_candidate(rag_service, candidate, check, run_context) -> ExplanationWithRefs
persist_candidate_check(conn, run_id, candidate_id, check, explanation) -> None
resolve_public_evidence(conn, refs, principal_scope) -> list[PublicEvidence]
```

### 1. `verify_baby_candidate` (`src/engine/stage3c_verify.py`)

- **사실 기반 규칙(카테고리 무관)**: `_recall_issue`/`_certification_issue`가
  `candidate.facts`(P2가 `catalog.product.attributes.facts_by_key`에 저장한 실제 시드
  데이터)를 읽어 "활성 리콜 검증됨" → `eligibility=fail, selection_allowed=False`,
  "인증번호 unknown" → `eligibility=unknown, selection_allowed=False`를 만든다. 둘 다
  실제 시드 픽스처(`SYN-BOTTLE-RECALL-001`, `SYN-CARSEAT-CERT-001`)로 검증했다(VE03).
- **설명서 기반 규칙**: `src.rag.verification.MANUAL_RULE_INVENTORY`에 등록된 슬롯(현재
  `stroller` 하나 — 이 환경에 존재하는 유일한 실제 설명서가 유모차이기 때문)만
  `verify_baby_manual`/`verify_seat`를 실행한다. 등록되지 않았지만 "리뷰된 무해당"으로
  선언된 15개 슬롯(`REVIEWED_NOT_APPLICABLE`)은 `pass`를 반환하되 그 근거(왜 통과인지)를
  issue로 명시해 남긴다. **두 딕셔너리 모두에 없는** 슬롯은 조용히 `pass`가 되지 않고
  `unknown`(`reason=no_reviewed_rule_for_category`)이 된다 — "규칙 부재"와 "검토된
  무해당"을 구분하라는 CONTRACTS §2 요구사항.
- **오류 구분**: RAG 검색이 `status=error`(임베더 실패/SQL 실패)면 `coverage=error`,
  `error_code`를 그대로 노출하고 `no_evidence`로 뭉개지 않는다(VE07).
- **synthetic 라벨**: `verify_seat`가 이미 `is_synthetic=request.corpus=="synthetic"`을
  붙이고, 이 함수는 그 값을 그대로 통과시킨다 — 합성 코퍼스를 실제 인증으로 해석하지
  않는다.

### 2. `explain_baby_candidate` (`src/engine/stage5_explain.py`)

검증과 **다른 질의**("제품 사양과 특징 설명")로 `explain_manual`(purpose=recommendation)을
호출한다. `verify_seat`는 내부적으로 항상 "좌석 모드 월령 체중 필수 조건"을 사용해 S01
섹션만 인용하므로, 두 함수의 인용 근거가 실제로 달라진다(구현으로 강제한 것이 아니라
실측으로 확인됨 — `test_ve05_verification_and_explanation_refs_can_differ`가 검증 근거는
전부 `S01`, 설명 근거는 `S01`이 아닌 다른 섹션임을 assert한다).

### 3. `persist_candidate_check` (`src/repo/engine_repo.py`)

- 트랜잭션을 열고 candidate가 실제로 해당 `run_id` 소속인지 `FOR UPDATE`로 잠근 뒤
  확인한다(아니면 `candidate_not_in_run`).
- **쓰기 전에 전부 검증**: `issue.evidence_ids`/`explanation.refs`의 모든 evidence_id를
  `EngineRepo.resolve_evidence_ref`로 재조회해 (a) 존재하는지(orphan이면
  `orphan_evidence_ref`), (b) `evidence.evidence.status='active'`인지(철회됐으면
  `revoked_evidence_ref`), (c) 그 evidence가 속한 `rag.retrieval_run.recommendation_run_id`가
  이번 `run_id`와 같은지(다르면 `cross_run_evidence_ref`), (d) 재구성한 필드가
  `src.reduction_contracts.EvidenceRef` 계약을 통과하는지(실패하면
  `malformed_evidence_ref`) 확인한다. 넷 중 하나라도 실패하면 **그 후보에 대해 아무 행도
  쓰지 않고** 예외를 던진다 — 검증을 먼저 전부 끝내고 실제 INSERT는 그 다음에 한다.
- 통과한 것만 `add_validation`/`link_validation_target`/`link_validation_evidence`(검증
  근거)와 `link_candidate_evidence`(설명 근거, `claim_key="explanation"`)로 실제 저장한다.

### 4. `resolve_public_evidence` (`src/repo/rag_repo.py`)

인용을 반환하는 시점에 재검사한다 — `ref`가 가리키는 자재/평가/공개 상태를 신뢰하지
않고, evidence가 속한 `rag.retrieval_run.scope_snapshot`(원래 `SearchRequest`를 그대로
얼려둔 것)으로 `SearchRequest`를 재구성해 `resolve_evidence`를 다시 태운다.
`principal_scope["recommendation_run_id"]`가 evidence의 실제 소속 run과 다르면
`out_of_scope`로 막는다(다른 사람의 실행 결과에서 근거를 읽을 수 없다). 철회되거나
다른 이유로 재검사에 실패하면 `available=False, text=None`이지만 `evidence_id`/`locator`
추적은 유지한다 — 근거가 있었다는 사실 자체를 지우지 않는다(VE06).

## 왜 `complete`가 아니라 `partial`인가

CONTRACTS.md의 종료 조건 원칙(P0/P1/P2 보고서와 동일)에 따라, 이 보고서가 스스로
`complete`를 선언하지 않는다. 그와 별도로, 정직하게 남는 경계는 위 `remaining` 블록과
같다 — 요약하면: (1) 이 환경에 실제 설명서가 유모차 하나뿐이라 `MANUAL_RULE_INVENTORY`가
그 하나만 담고 있고 나머지는 "검토된 무해당"으로 명시 선언했을 뿐 외부 안전 심사를 거친
목록은 아니다, (2) HTTP/파이프라인 배선은 CONTRACTS가 명시한 대로 P5 소관이라 이 과업
범위 밖이다, (3) `corpus=real`은 실제 벤더 데이터가 없어 이번에도 실행되지 않았다(P2와
동일한 경계), (4) P1의 정확값/대표값 버그(R2)는 고쳐지지 않았고, 이 과업은 그 값을
있는 그대로 받아 안전 쪽으로(대표값을 정확값처럼 쓰지 않고 unknown 유발) 처리할 뿐이다.
