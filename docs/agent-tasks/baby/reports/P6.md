# P6 execution report — 가입·비밀번호 인증·설정·게스트 인계

## 실행 요약

이 과업 시작 시점에 `src/routers/auth.py`/`auth_service.py`는 옛 "이메일 6자리 코드"
스켈레톤이었고(가입/로그인/탈퇴 전부 `NotImplementedError` 또는 데모 스텁), 실제로 쓰이는
DB 스키마(`identity.app_user`의 `password_hash`, `failed_login_count`, `locked_until`,
`terms_agreed_at` 등)는 이미 `db/migrations/0007_app_user_password_auth.sql`(선행 커밋)에
존재했지만 이를 소비하는 서비스/라우터 코드는 없었다. 이 과업은 그 위에 실제 이메일+비밀번호
인증 전체 경로를 새로 구현했다 — 새 파이프라인이나 DB mock을 만들지 않고, P1 이 만든
`session_service.load_owned_draft`/`PlanRepo`/`ConversationRepo`/`truefit_guest` 소유권
모델을 그대로 재사용해 게스트→계정 병합을 얹었다.

## 구현 내용

1. **비밀번호 해싱** (`src/auth/passwords.py`) — argon2-cffi(명시적으로 버전 고정,
   `pyproject.toml`) 로 `PasswordHasher().hash()`; 인코딩된 해시 문자열 자체에 알고리즘/버전/
   salt/파라미터가 모두 들어 있어 별도 컬럼이 필요 없다. 미존재 계정에도 같은 연산 시간이
   걸리도록 `dummy_verify()` 를 둬 계정 존재 여부가 응답 시간으로 새지 않게 했다.
2. **가입** (`auth_service.signup`) — 이메일 trim+lower 정규화, 비밀번호 8~128자+영문+숫자,
   표시 이름 1~20자, 약관 필수 검사 후 UUID를 먼저 만들어 `id`와 `auth_subject='local:<uuid>'`
   에 같이 넣고 `identity.app_user` 1행을 트랜잭션 안에서 만든다. 같은 트랜잭션 안에서 유효한
   `truefit_guest` 쿠키가 있으면 그 게스트가 소유한 대화/plan을 병합한다. 동시 가입 경쟁으로
   유니크 제약이 걸리면 `psycopg.errors.UniqueViolation` 을 잡아 `409 email_taken` 으로
   변환한다(DB 유니크 인덱스가 최종 방어선).
3. **로그인 실패/잠금** (`auth_service.login`, `UserRepo.increment_failed_login`/
   `lock_and_reset_count`) — 미존재 이메일은 더미 Argon2 검증 후 오답과 동일한
   `401 invalid_credentials`. 오답은 `failed_login_count = failed_login_count + 1` 을
   원자적 UPDATE로 실행(같은 행에 대한 동시 UPDATE는 Postgres 행 잠금으로 직렬화되어 유실되지
   않음 — 스레드 5개로 실측). 5번째 오답에서 카운트를 0으로 되돌리고 `locked_until = now() +
   15분` 을 설정한다. 잠금 중에는 비밀번호가 맞아도 검증 전에 `423 account_locked` 을 반환한다.
   **중요한 구현 세부사항**: 이 실패 기록은 최종적으로 401을 반환하는 요청 안에서 일어나는데,
   `src/db.get_conn()` 은 예외가 나면 트랜잭션 전체를 롤백한다 — 그대로 두면 잠금 카운트
   증가분이 요청 실패와 함께 사라진다. 그래서 실패 카운트/잠금 UPDATE만 별도의
   `get_conn()` 커넥션(짧은 독립 트랜잭션)으로 즉시 커밋하고, 그 다음에 원래 요청의
   `Unauthorized`/`AccountLocked` 를 던지도록 분리했다. 이 문제를 실제로 재현했고(첫 구현은
   5번 오답 후에도 `locked_until` 이 계속 NULL이었다) 고쳐서 실측 검증했다(아래 검증 절 참고).
4. **auth_version 하드닝** (신규 `db/migrations/0015_auth_version.sql`, `src/auth/jwt.py`,
   `src/auth/deps.py`) — CURRENT BASELINE 델타가 지적한 "iat 초 단위 비교의 동시 초 재발급
   경쟁" 허점을 없애기 위해, 원래 프런트 문서(§A-3)가 제안한 `password_updated_at` 초단위
   비교 대신 단조 증가 `auth_version` 정수를 `identity.app_user`에 추가했다. JWT는 발급
   시점의 `auth_version` 을 클레임에 싣고, `src.auth.deps._authenticate()` 가 서명·만료
   검증 후 **매 인증 요청마다 DB를 다시 조회**해 계정 `status='active'` 와 `auth_version`
   일치를 확인한다. 비밀번호 변경/탈퇴가 `auth_version` 을 올리면 그 순간 이전 토큰은 서명이
   유효해도 즉시 거부된다 — 같은 초 안에 발급된 토큰도 예외 없이 막힌다(AU04 실측, 아래).
5. **쿠키** (`src/routers/auth.py`) — `truefit_session`, HttpOnly, `SameSite=lax`, `Path=/`.
   `remember=true` → `Max-Age=JWT_TTL_DAYS`(14일)일 JWT 발급. `remember=false` → 브라우저
   세션 쿠키(Max-Age 없음) + 서버 측 12시간 만료 JWT(`JWT_SESSION_TTL_HOURS`). `Secure` 는
   `APP_ENV=production` 이거나 `AUTH_COOKIE_SECURE=1` 일 때만 켜진다 — 로컬 HTTP 검증에서는
   꺼져 있는 것을 실측 확인했다(`test_au02_cookie_flags_match_local_http_environment`).
   운영 환경에서 기본 개발용 `JWT_SECRET` 을 그대로 쓰면 `assert_production_secret_safe()`
   가 앱 시작 시 `RuntimeError` 로 막는다(`src/api.py` lifespan에서 호출).
6. **게스트 병합** (`ConversationRepo.merge_guest_into_user`) — P1의 소유권 판단 기준인
   `identity.conversation.user_id`/`guest_session_hash` 를 그대로 따른다. 서명/가입 시
   전달된 `truefit_guest` 값이 실제로 존재하는 해시인지(`guest_identity_known`) 먼저 확인한
   뒤에만, 그 해시로 만들어진 모든 대화의 `user_id` 를 채우고 `guest_session_hash` 를
   `NULL` 로 지운다(원자적 UPDATE 1개) — 이후 같은 쿠키로는 그 대화/plan에 다시 접근할 수
   없다. 위조/미지 토큰은 조용히 무시한다(다른 사람 정체성을 훔쳐 붙이지 않음).
7. **프로필/비밀번호/탈퇴** — `PATCH /auth/me` 는 email 변경 시 `email_verified_at` 을
   `NULL` 로 지우고, 이메일 중복은 DB 유니크 제약 위반을 잡아 `409 email_taken`으로도 방어한다
   (경쟁 상황 최종 방어선). `marketing_agreed` 는 `marketing_agreed_at` 시각으로 저장/제거
   (별도 boolean 컬럼 없음, 기존 0007 마이그레이션 스키마 그대로). 탈퇴는 현재 비밀번호를
   확인한 뒤 `status='deleted'`, `deleted_at=now()`, 이메일/이름을 `deleted-<uuid>@...`/
   `'탈퇴한 사용자'`로 익명화하고 비밀번호 해시·약관·마케팅 동의·이메일 인증 시각을 지운다.
   `identity.app_user` 를 참조하는 FK는 전부 `ON DELETE RESTRICT`(0003 마이그레이션)라 행
   자체는 남아 plan/conversation 이력 참조가 깨지지 않는다 — 카탈로그/리뷰 집계를 연쇄
   삭제하지 않는다. `auth_version` 을 올려 즉시 모든 기존 토큰을 무효화한다. 같은 이메일로
   재가입이 가능함을 실측했다(익명화된 이메일이 원래 이메일 자리를 비워줌).
8. **보류된 레거시 엔드포인트** — `docs/frontend_외부수정요청.md` §A-4 각주("삭제하지 말고

## 미충족/외부 조건 (구현·검증 결과와 구분)

- Origin/mutation 정책은 앱 전체에 존재하지 않는다(코드 검색으로 확인; CORS/Origin
  미들웨어 없음). CONTRACTS는 "P1 정책을 재사용"하라고 하지만 P1도 이를 구현하지 않았고,
  이를 새로 만드는 것은 `src/api.py` 전역 미들웨어를 건드려야 해 이 과업의 edit surface
  밖이다. 고정된 성공 응답으로 감추지 않고 그대로 미해결로 남긴다.
- 실제 브라우저(Chrome 등) 조작 스모크는 실행하지 않았다 — CONTRACTS/VERIFY가 이를 "P5
  의존성 확보 후"로 조건부로 뒀는데 P5는 여전히 partial(`reports/P5.md`)이다. 대신 실제
  PostgreSQL + 실제 FastAPI 요청/응답 주기로 모든 인수 조건을 검증했다(mock 아님).
- 로그아웃은 전 세션 서버측 폐기가 아니라 이 브라우저 쿠키 삭제로 범위를 명확히 한정했다
  (RULES #9에 따른 문서화된 선택 — 세션 테이블이 없어 기기별 폐기는 이번 범위 밖).
