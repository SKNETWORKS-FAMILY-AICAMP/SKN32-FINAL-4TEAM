# 유아용품 장바구니 수정 에이전트 작업 지시서

작성일: 2026-09-14 · 조사 기준 커밋: `b6faf9d`

## 목표와 현재 판정

유아용품 웹 흐름을 **신규 장바구니 → 조건 입력 → 근거에 따른 추천 → 담기·수량·삭제·교체 → 로그인·확정 → 리포트·재조회**까지 검증 가능하게 수정한다. 검증 근거가 부족한 상품은 선택을 막되, 사용자가 이유와 다음 행동을 알 수 있어야 한다.

이 문서는 수정 지시서다. 앱 수정은 아직 수행하지 않았다. 근거는 [실제 브라우저 테스트 보고서](baby-cart-browser-test-2026-09-14.md) 및 연결된 스크린샷이다. 기존 단위·HTTP 테스트 통과를 웹 전체 흐름 완료로 간주하지 않는다.

## 시작 전 확인

1. 현재 작업 트리와 `AGENTS.md`를 확인하고 다른 변경을 보존한다. 아래 경로·함수는 현재 코드에서 다시 찾는다.
2. [기존 작업 목록의 ENTRYPOINT 절](agent-tasks/baby/README.md#entrypoint)에 따라 `DEVELOP_DB_TRANSITION.md`, `schema-v1.md`, `CONTRACTS.md`를 읽는다. 오래된 문서의 구현 상태보다 현재 코드와 재현 결과를 우선 확인한다. 삭제된 PostgreSQL `rag` 스키마나 구 테이블을 복원하지 않는다.
3. 전용 임시 PostgreSQL과 기본 합성 카탈로그로 재현한다. 기존 DB 삭제·초기화 금지. DB가 필요한 테스트의 대상 연결 문자열을 실행 전에 확인한다.
4. 현재 재현: 홈 → 장바구니 만들기 → 유아용품 → 0~3개월 → 기저귀·배변 → 특이사항 없음 → 보유 물품 없음 → 예산 100만원 → 추천. 상품 0개, 확정 disabled.

## A. 선택 가능한 검증 경로와 근거 데이터 완성

### 원인

- `src/rag/verification.py:14`: `MANUAL_RULE_INVENTORY`에 `stroller`만 있고 `REVIEWED_NOT_APPLICABLE`은 비어 있다.
- `src/engine/stage3c_verify.py:283`: 두 목록에 없는 품목은 `no_reviewed_rule_for_category`, `eligibility=unknown`으로 분류한다. 298행에서 pass만 `selection_allowed=True`가 된다.
- `src/engine/stage4_optimize.py`의 `_eligible_priced`가 선택 불가 후보를 제외한다. 필수 기저귀·물티슈의 후보 풀이 비어 장바구니가 완성되지 않는다.
- 실제 PostgreSQL의 `engine.validation_result`에서 해당 품목들의 unknown·규칙 부재 사유를 확인했다. 단순 상품 수 부족이나 100만원 예산 부족이 아니다.

### 구현 지시

1. `config/baby_requirement_rules.yaml`이 만드는 품목과 기본 카탈로그의 품목별로 검증 규칙·필요 근거·근거 보유 여부를 대응시킨다. 누락 항목을 목록으로 남긴다.
2. 기존 근거 계약과 자료를 이용해 검증 가능한 품목의 규칙 및 자료 적재 경로를 구현한다. 규칙마다 적용 범위, 버전, 필수 입력, 출처, pass/fail/unknown 조건을 명시한다. 실제 제품 안전 기준을 새로 정해야 한다면 공식 원문·확인 날짜가 필요하며 임의 기준을 만들지 않는다.
3. 비적용 처리는 검토 근거가 있는 규칙에만 사용한다. 기저귀·물티슈를 목록에 일괄 추가하거나 `unknown → pass`로 바꿔 통과시키지 않는다.
4. 합성 자료로 검증하는 개발 시나리오는 합성임을 유지한다. 기존 검증기의 조건을 실제로 만족하는 자료·카탈로그를 일반 적재 경로로 준비하고 브라우저에서도 같은 결과가 나오게 한다. 테스트 전용 `CandidateCheck(pass)` 주입을 웹 완료 증거로 사용하지 않는다.
5. 검증 규칙·공식 근거가 아직 없는 품목은 B의 구체적 차단 사유를 제공한다. 별도의 검증 가능한 유아 시나리오로 편집·확정·리포트까지 테스트하되, 원래 기저귀 시나리오 미해결을 숨기지 않는다.
6. 가입·편집·확정 API의 선택 가능성 검사도 유지한다. UI에서만 막는 방식으로 바꾸지 않는다.

### 수용 기준

- 검증 가능한 기본 개발 시나리오에서 실제 추천 결과의 상품 수가 1 이상이며 구매선 확정까지 진행한다.
- 알려진 불충족, 규칙 미정, 입력 부족, provider 미설정, 근거 없음은 정확한 상태로 남고 강제 선택·확정되지 않는다.
- 원래 기저귀·물티슈 사례의 해결 여부와 남은 근거 요구사항을 별도 보고한다. 임의 승인만으로 A 완료 처리 금지.

## B. 실패 사유를 API·화면까지 보존

### 원인

`src/services/recommendation_service.py:399`은 feasible 여부만으로 headline을 고른다. 검증 실패·근거 부족도 예산 부족으로 바뀐다. 최적화 결과에는 `missing_requirements`가 있지만 최종 화면에 필요한 상세 차단 사유 전달이 부족하다. `get_stored_result`와 프런트 결과 렌더링까지 추적해야 한다.

### 구현 지시

- 최소한 규칙 부재, 검증 입력 부족, 검색 제공자 미설정/실패, 근거 없음, 적용 조건 불충족, 가격·재고 문제, 실제 예산 초과를 구별한다. 여러 사유가 공존할 수 있도록 설계한다.
- 기존 CandidateCheck·최적화 결과·검증 기록을 활용하고 새로운 독립 판정 로직을 프런트에 만들지 않는다.
- 품목 식별자와 안정적인 사유 코드, 사용자 설명, 다음 행동을 결과 응답에 전달한다. 공개 DTO를 확장하면 producer·schema·consumer·테스트를 함께 맞춘다.
- 빈 장바구니에서 ‘조건에 맞춰 구성했어요’라는 성공형 문구를 표시하지 않는다. 중복 headline/text도 정리한다.
- 재조회 후에도 사유를 보존한다. 조회만으로 검색·추천을 다시 실행하지 않는다.

수용 기준: 기저귀 규칙 부재는 ‘검증 기준이 준비되지 않아 담을 수 없음’에 해당하는 안내를 하고, 예산만 늘리도록 유도하지 않는다. 실제 비용이 초과하는 별도 사례에서는 정확한 부족액과 예산 안내를 한다.

## C. 명시적인 ‘없음’과 미응답 구별

### 원인

`src/services/session_service.py:431`은 없음 응답을 `[]`로 저장한다. 같은 파일 `_display`의 182행이 이를 `None`으로 바꾸고, `frontend/js/pages/conditions.js`는 표시값이 없으면 ‘아직 확인되지 않았어요’를 출력한다. 조건은 충족했으나 요약만 미응답처럼 보인다.

### 구현 지시

- 현재 빈 배열 정규화 계약을 보존하면서 응답 여부·필드 상태에 따라 없음과 미응답을 표시한다. 모든 빈 배열을 무조건 없음으로 바꾸지 않는다.

수용 기준: 두 없음 응답은 confirmed 상태의 명시적 문구로 보이고, 필드 초기화 후에는 missing으로 되돌아가며 필요하면 추천 가능 여부도 갱신된다.

### 원인

- `frontend/js/pages/results.js`의 `tfResultSummaryHtml`은 도메인과 무관하게 ‘부품’ 표현을 사용한다.
- `src/services/recommendation_service.py:843`의 `handle_result_message`는 에이전트 사용 불가 시 `_parse_swap_request` 규칙 경로로 간다. 이 경로는 가격 방향이 있는 교체 요청 중심이며 PC용 실패 문구를 반환한다.
- `src/agent/result_agent.py`의 `available()`은 MOCK_MODE·설정·키에 따라 false가 된다. 테스트 환경은 MOCK_MODE=1이므로 규칙 경로다. LLM 연결만 켜면 해결된다고 간주하지 않는다.

### 구현 지시

- 도메인별 품목 표현과 예시를 분리한다. 유아 화면에 ‘그래픽카드’, ‘부품’이 기본 안내로 나오지 않게 한다.
- 기존 검증된 편집 서비스·에이전트 도구를 확인하고, 기본 규칙 경로에서 유아 품목의 명확한 담기·빼기·수량 변경·교체 요청을 지원한다. 가능한 UI 동작도 연결한다.
- 요청 문구를 이해한 것과 실제 선택 가능 여부를 분리한다. ‘기저귀 담아줘’를 이해했더라도 A의 unknown이면 사유를 설명하고 상태를 변경하지 않는다.
- 다수 후보 또는 대상이 애매하면 후보를 제시하거나 되묻는다. 첫 번째 행을 임의 선택하지 않는다. PC용 후보 조회가 유아 경로에 적용되지 않는지 확인한다.
- LLM 미사용 경로를 먼저 검증한다. 외부 모델 경로를 확인했다면 별도 결과로 기록한다.

수용 기준: 유효한 유아 상품에 대한 편집은 서버 상태·합계와 함께 반영되며, 불가 상품에는 정확한 거절 사유가 나온다. PC 결과 채팅 회귀 테스트도 통과한다.

## E. 모바일 슬라이드 영역 진단·수정

### 근거와 추정 원인

- 관찰값: viewport 390px에서 document scrollWidth 780px. [모바일 증거](baby-cart-browser-artifacts-2026-09-14/mobile.png)의 오른쪽 빈 패널 참고.
- `frontend/css/planner.css:224`: `.cart-review-slide`가 `position:absolute`, `width:100%`, `transform:translateX(100%)`인 채 DOM에 존재한다.
- 같은 파일 152행의 max-width 900px 규칙은 `.result-cart{position:static}`으로 바꾼다. 절대 위치 패널의 기준 영역이 달라져 가로 넘침이 생기는 것이 유력하다.
- 닫힌 패널을 DOM에서 일시 숨겨 scrollWidth를 비교하려던 추가 브라우저 진단은 자동 승인 검토 서비스의 모델 용량 오류로 실행 거절됐다. 특정 수정안의 효과는 아직 실측하지 않았으며, 다음 에이전트가 먼저 확인해야 한다.

### 구현 지시와 수용 기준

1. 닫힌 패널·열린 패널·부모의 bounding rect, computed position/transform/overflow를 기록한다. 패널을 브라우저에서만 일시 숨겨 가로 넘침이 해소되는지 비교한다.
2. 모바일에서도 의도한 containing block을 유지하고, 닫힌 패널이 레이아웃·스크롤·탭 탐색에 참여하지 않게 한다. body 전체 overflow 숨김만으로 결함을 덮지 않는다.
3. 패널 열기·닫기, Escape, 배경 클릭, 내부 스크롤, 포커스 복귀, 수량·확정 버튼 접근을 확인한다.
4. 390×844, 768px 폭, 1440px 폭에서 닫힘·열림 모두 `scrollWidth <= innerWidth + 1`을 확인한다. 화면 외부로 중요한 콘텐츠가 잘려 사라지지 않아야 한다.

## 작업 순서와 통합 책임

C·E는 독립 수정 가능하다. A는 검증 가능한 데이터와 상태를 제공하고, B는 이를 사용자에게 전달한다. D는 기존 편집 서비스의 검증을 재사용한다. A와 B가 연결된 뒤 전체 브라우저 검증을 수행한다.

여러 에이전트가 맡는 경우 `recommendation_service.py`와 결과 DTO의 최종 통합 담당자를 한 명 정한다. A·B·D가 같은 파일을 각자 덮어쓰지 않는다. 담당자는 진행 중 변경을 먼저 반영하고 충돌을 해결한다. 이 문서 작성 자체는 에이전트 실행·배포 지시가 아니다.

- 편집·확정: `tests/test_result_interaction.py`, `tests/test_result_agent.py`, `tests/test_list_service.py` — 기존 PC 테스트만으로 유아 통과를 주장하지 않는다. 유아 사례를 추가한다.
- `tests/test_baby_recommendation_http.py`의 `_seed_editable_to_purchase_item`은 판정을 주입하는 편집 테스트 fixture다. 이를 이용한 통과는 편집 기능의 근거이며 일반 추천 성공의 근거가 아니다.

실제 브라우저에서 다음 전체 흐름을 실행하고 HTTP 상태·서버 결과·스크린샷을 남긴다.

1. 신규 게스트 장바구니, 유아 조건 입력, 명시적인 없음 응답 확인.
2. 실제 자료를 거친 추천으로 1개 이상 선택. 불가 상품의 이유 표시도 별도 확인.
3. 수량 증가·감소와 최소/최대 경계, 가격×수량 및 총액 일치.
4. 담기·개별 제거·재추가·대체 후보·구매 시점 변경. 재조회 시 상태 보존.
5. 예산 초과·빈 바구니·검증 불가 항목의 확정 차단. 유효 바구니는 확정 가능.
6. 테스트 계정 로그인 또는 가입, 게스트 장바구니 인계, 확정 입력값 유지, 확정 저장.
7. 리포트의 품목·수량·금액 일치, 새로고침·재로그인 후 재조회. 확정 스냅샷 보존.
8. 새 장바구니 생성·전환·이름 변경·테스트 장바구니 삭제. 다른 장바구니에 영향 없음.
9. 모바일 패널과 장바구니 조작, PC 카테고리 주요 회귀.

API 응답을 가짜로 대체하거나 DB 선택 플래그를 직접 바꾼 브라우저 실행은 위 전체 흐름의 통과로 계산하지 않는다. 권한·소유권·동시 수정·검증 불가 선택 금지 검사를 완화하지 않는다.

## 인계 산출물과 완료 판정

- 수정 파일과 원인→수정 내용 대응표.
- 필요한 규칙·자료·provider 설정 및 멱등한 개발 환경 준비 방법. 비밀 키 값은 기록하지 않는다.
- 실제 실행한 테스트 명령·통과/실패/skip 수와 의미, 브라우저 재현 스크립트, 스크린샷, 관찰한 API 상태.
- 원래 기저귀 시나리오와 검증 가능한 성공 시나리오를 분리한 결과.
- 미해결 항목은 필요한 데이터·검토·환경 조건을 구체적으로 적는다. 테스트 환경 장애를 앱 결함으로 보고하지 않는다.

검증 자료가 없어 A를 완성하지 못했으면 B~E와 가능한 회귀 검증은 마무리하되 **전체 정상 동작 완료라고 보고하지 않는다**. 전체 게이트를 통과하고 원래 시나리오의 상태까지 설명할 수 있을 때 최종 인계한다.
